## 0.1 🖊️ Signature Flow Addendum (locked 2026-09-23, หลัง CEO ให้รายละเอียดเพิ่ม + verify โค้ดจริงรอบ 2)

CEO ต้องการ flow เฉพาะ: ผู้เซ็นล็อกอินผ่าน LINE → ลายเซ็นผูกกับตัวเอง (บันทึกไว้ใช้ซ้ำ) → เปิดดูเอกสารเต็มฉบับ + เห็นตำแหน่งที่ลายเซ็นจะไปแปะก่อนกดยืนยัน → ลายเซ็น PNG แปะทันทีตอนอนุมัติ

**Verify รอบ 2 (อ่านโค้ดจริง):**
- **บันทึกลายเซ็นไว้ใช้ซ้ำ**: ไม่มีในระบบเลยตอนนี้ (`User` model ไม่มี field เก็บลายเซ็น, `DocumentSignaturePlacement.signedImageKey` เก็บทีละครั้งต่อการเซ็น ไม่ใช่ต่อ user) — **ต้องสร้างใหม่**: เพิ่มที่เก็บลายเซ็นต่อ user (เช่น field ใหม่ใน User หรือตารางแยก) + หน้า "ตั้งค่าลายเซ็นของฉัน"
- **พรีวิวก่อนเซ็น**: ตอนนี้ (`signer-interface.tsx`) โชว์แค่หน้าเดียวที่มีช่องเซ็น ไม่ใช่เอกสารทั้งฉบับ และวาดลายเซ็น+ส่งเป็น action เดียวกันในหน้าต่างเดียว ไม่มีขั้น "ดูก่อน-ยืนยันทีหลัง" แยกกัน — **ต้องเพิ่ม**: หน้าพรีวิวเต็มเอกสารทุกหน้า (เห็นทุกตำแหน่งที่ลายเซ็นจะไปแปะ) ก่อนเข้าสู่ขั้นวาด/ยืนยันลายเซ็น
- **LINE Login สำหรับผู้เซ็น**: ยืนยันแล้วว่าคนที่เซ็นผ่าน LINE Login ของระบบนี้เป็น **พนักงาน/คนในบริษัทเท่านั้น 100%** (CEO ยืนยัน 2026-09-23) ตรงกับพฤติกรรมจริงของ LINE Login ที่มีอยู่ (`app/auth/line-callback` → `ensurePoolMembership` สร้างบัญชี staff เต็มรูปแบบเสมอ) — **ใช้ LINE Login เดิมได้ตรงๆ ไม่ต้องสร้างระบบสิทธิ์ใหม่** เพราะผู้เซ็นทุกคนควรมีบัญชีในระบบอยู่แล้วโดยธรรมชาติของงาน (ไม่ใช่คนนอกบริษัท)

**สรุป Signature Flow ที่จะสร้าง:**
1. หน้า "ตั้งค่าลายเซ็นของฉัน" (วาด/อัปโหลดครั้งเดียว บันทึกไว้ผูกกับบัญชีผู้ใช้)
2. เมื่อมีเอกสารรอเซ็น → เปิดผ่าน LINE Login (ของเดิม ไม่ต้องสร้างใหม่) → เจอหน้าพรีวิวเอกสารเต็มฉบับ เห็นทุกตำแหน่งลายเซ็น
3. กดยืนยัน → ระบบดึงลายเซ็นที่บันทึกไว้ (ข้อ 1) แปะลง PDF ทันที (reuse `embedSignatures()` เดิมที่ทำงานได้อยู่แล้ว)
4. ถ้าผู้ใช้ยังไม่เคยบันทึกลายเซ็น → ให้วาดครั้งแรกพร้อมถามว่า "บันทึกไว้ใช้ครั้งต่อไปไหม" ก่อนเซ็น

## 1. 🎯 Goal & Success Metrics

**เป้าหมาย:** ลดความสับสนของเมนู DocuFlow (ปัจจุบัน ~22 route จริง ไม่มี desktop sidebar เลย มีแค่ mobile bottom nav 5 ปุ่ม) ให้เจ้าหน้าที่ธุรการที่ใช้งานผ่านมือถือหาของเจอเร็วขึ้น และปรับหน้าตาให้เข้าตระกูลเดียวกับ ChairOps/CashHub/RentSpace ที่ CEO สร้างไว้แล้ว

**Success metric ที่เสนอ (BA seat):**
- จำนวนเมนูหลักบน bottom nav: 5 (เท่าเดิม แต่เนื้อหาเปลี่ยน — เดิมมีของซ้ำซ้อน 3 หน้าที่ทำหน้าที่ "หาเอกสาร" เหมือนกัน)
- ปุ่ม/แท็บที่กดแล้วไม่มีผล (dead UI): ปัจจุบันอย่างน้อย 2 จุดที่ยืนยันแล้ว (แท็บ filter ใน `/browse`, ลิงก์ "ตั้งค่าประเภทเอกสาร") → target = 0
- Timed test: ให้เจ้าหน้าที่ธุรการ 2-3 คนจับเวลา "หาใบอนุญาตที่ใกล้หมดอายุ" ก่อน/หลัง

**Definition of Done (Phase 1 เท่านั้น — ดู §6):** เมนูใหม่ deploy จริง, filter ทำงานจริงทุกปุ่ม, ไม่มีตัวเลข/สถิติปลอมเหลืออยู่ในหน้าใดๆ ของโมดูล

## 3. 🗣️ Debate Highlights

- **Scope creep ที่เกือบไม่มีใครทัก**: CEO's brief 16 ข้อ มี effort ต่างกันสิบเท่า — 10 ข้อ (เมนู/filter/settings shell) reuse pattern ที่มีอยู่แล้วในโค้ด effort ต่ำ ส่วน 2 ข้อ (Google Drive, LINE OA) เป็น integration ใหม่ทั้งหมด effort สูงกว่าที่เหลือรวมกัน — Devil's Advocate + PM + Project Owner ต่างคนต่างคิดเจอเรื่องเดียวกันโดยไม่ได้คุยกันมาก่อน (convergent, ไม่ใช่ copy ความเห็นกัน) → ตกลงแยก 2 track
- **Google Drive — เถียงกันจริงระหว่าง R1/R2**: Architect/SA/Senior Programmer เสนอ reuse OAuth ต่อบุคคลแบบเดิม (`lib/chairops/storage/drive.ts`, effort ต่ำสุด) แต่ Domain Expert A ค้านตรงๆ ว่าเอกสาร DocuFlow อ่อนไหวกว่า (บัตร ปชช./ภาษี) เสนอ Service Account+Shared Drive แทน — R2 คลี่ปมด้วยการถาม Devil's Advocate กลับว่า "ทำไมต้องมี Drive เลย ในเมื่อ R2 storage เดิมทำงานดีอยู่แล้ว" → ได้ทางออกที่ 3 ที่ทั้งถูกกว่าและปลอดภัยกว่า 2 ทางแรก: ปุ่ม "Export ไป Drive" แบบเลือกไฟล์ (one-way, opt-in ต่อคน ไม่ใช่ access-gate ขององค์กร) ดู §7 Q2
- **LINE OA — เจอ precedent ที่ดีกว่าหลัง R1 จบไปแล้ว**: R1 ทุกคนเข้าใจว่าต้องสร้างใหม่ทั้งหมดเพราะ `chairops/line/notify.ts` ใช้ LINE Notify ที่เลิกให้บริการแล้ว (มี.ค. 2025) — R2 verifier ไปเจอว่า `LedgerLineChannel` (schema.prisma:7225+) เป็น LINE **Messaging API** ที่ใช้งานได้จริง (ไม่ใช่ LINE Notify) มี push function จริง (`lib/ledger/line-push.ts:45-98`) เข้ารหัส AES-256-GCM ต่อบริษัท — เปลี่ยน estimate ของ LINE OA จาก "สร้างทุกอย่างจากศูนย์" เป็น "มี pattern ตารางอ้างอิงจริง แค่ต้องคัดลอกโครงสร้าง" ⚠️ แต่เจอกับดักซ้อนอยู่ในนั้น: key เข้ารหัสของ Ledger ชื่อ `RECRUIT_CHANNEL_KEY` — เป็น env ชื่อโมดูลอื่นที่ไม่ตรงกับตัวเอง (ตรงกับ pattern อุบัติเหตุที่เคยเกิดจริงกับ inbox เมื่อ 2026-06-08) **ห้าม DocuFlow ใช้ key นี้ซ้ำเด็ดขาด — ต้องตั้ง `DOCUFLOW_LINE_CRYPTO_KEY` ของตัวเอง**
- **End User ชนะ 2 hard line โดยที่ระบบมีของรองรับอยู่แล้ว**: End User ยืนกรานว่า "ใกล้หมดอายุ" ต้องถึงได้ใน 1 แตะ และ Checklist ต้องดูได้แบบ read-only ไม่ใช่ admin-only — R2 ไปเช็คโค้ดจริงแล้วพบว่าหน้าแรก (`docuflow/page.tsx`) มี section ทั้งสองอย่างฝังอยู่แล้ว และหน้า checklist ใช้ `requireExecutiveRole` (ไม่ใช่ admin-tier) อยู่แล้ว — จึงไม่ใช่ "ของใหม่ที่ต้องสร้าง" แค่ "ห้ามทำให้แย่ลงตอน redesign" ⚠️ แต่พบ gap จริงคู่กัน: ไอคอนกระดิ่งแจ้งเตือนที่ header ถูกซ่อนบนมือถือ (desktop-only) — ถ้าตัดแท็บ "แจ้งเตือน" ออกจาก bottom nav โดยไม่เปิดกระดิ่งนี้ให้โชว์บนมือถือด้วย จะเสียการเข้าถึงจริงทันที (ต้อง ship คู่กัน)
- **หน้า "ตั้งค่า Workflow" ไม่ใช่แค่ "ยังไม่เสร็จ" — เป็นข้อมูลปลอมที่แสดงอยู่จริงตอนนี้**: ทุก seat ที่แตะประเด็นนี้ (PM, BA, SA, Senior Programmer, QA/QC, Project Owner, Devil's Advocate) ต่างคนต่างเจอเลข "เทมเพลตใช้ไปแล้ว 142 ครั้ง" ที่ hardcode ไว้ในโค้ด (`workflow/page.tsx` บรรทัด 48-70, render จริงที่บรรทัด 610) โดยไม่มี label ใดๆ บอกว่าเป็นตัวอย่าง — มติเอกฉันท์: ไม่ว่าจะตัดสินใจสร้าง workflow ให้จบในรอบนี้หรือไม่ **ต้องเอาตัวเลขปลอมออกจากจอทันที** เป็น hard requirement แยกจาก scope decision อื่น

## 4. ✅ Consensus Decisions (ทีมตกลงกันแล้ว ไม่ต้องรอ CEO)

1. **แบ่ง 2 track**: Track A = declutter (เมนู, filter จริง, settings shell, ฟอร์มอัปโหลดเลือกบริษัท/สาขา/ประเภท, multi-file) — effort ต่ำ ทำก่อน. Track B = Google Drive + LINE OA + Workflow เต็มรูปแบบ — effort สูงกว่า แยก phase ให้ CEO เห็นต้นทุนก่อนเริ่ม (ดู §7)
2. **DocumentType เป็น DB entity ใหม่ (ไม่ใช่ static array)** — ตอบโจทย์พร้อมกัน 4 ข้อ (checklist, type-picker ตอนอัปโหลด, filter ตามประเภท, หน้าตั้งค่าจัดการประเภทเอกสาร) เพราะทั้งหมดอ้างอิง `canonical-docs.ts` ตัวเดียวกันอยู่แล้ว — ใช้แบบ hybrid (DB entity + canonical-docs.ts เป็น seed/fallback) ไม่ migrate ข้อมูลเก่าแบบ auto-fuzzy-merge (เสี่ยงเอกสารผิดประเภทเงียบๆ) ต้อง manual review ก่อน backfill
3. **Multi-file upload**: loop เรียก endpoint เดิมทีละไฟล์ (ไม่ทำ batch API ใหม่) + UI ต้องโชว์สถานะรายไฟล์ (สำเร็จ/พลาด) ไม่ใช่ progress bar รวมอันเดียว
4. **Settings hub ใหม่**: ก็อป pattern จาก `recruit/settings/page.tsx` (hub + sub-routes) ตรงๆ ใช้ gate `userIsModuleAdmin` ที่มีอยู่แล้ว — ไม่คิด pattern ใหม่
5. **UI/design tokens**: repaint เต็มรูปแบบให้ตรงตระกูล CashHub/RentSpace (`#1e3aff` ฟ้า, พื้นขาว-zinc) แทนพาเลตต์ครีม+ฟอนต์ serif เฉพาะตัวที่ DocuFlow ใช้อยู่ตอนนี้ (ไม่ derive จาก token กลางเลย) — คง shape ของ component เดิมไว้ (แก้แค่สี ไม่ rewrite ทั้งหมด)
6. **"142 ครั้ง" ปลอมต้องออกจากจอทันที** ไม่ว่าจะเลือกทำ Workflow ให้จบในรอบนี้หรือไม่ (ดู §7 Q3) — พร้อม sweep หา mock-data-แสดงเป็นของจริงจุดอื่นในโมดูลก่อนปิดงาน
7. **บั๊กฟอนต์ไทยในลายเซ็น** (auto-fill ชื่อ/วันที่ไทยกลายเป็น "?" เพราะ Helvetica วาดไม่ได้) แก้ทันทีแยกจาก scope อื่น เพราะเป็นบั๊กข้อมูลที่ active อยู่ตอนนี้ ไม่ต้องรอ decision เรื่อง Workflow เต็มรูปแบบ
