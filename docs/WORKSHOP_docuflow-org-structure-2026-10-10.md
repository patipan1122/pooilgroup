# Workshop · DocuFlow — จัดระเบียบเอกสารของตัวเอง

## 1. 🎯 Goal & Success Metrics

**เป้าหมายธุรกิจ:** พนักงานธุรการหาเอกสารเจอเร็วขึ้น จัดระเบียบเองได้โดยไม่ต้องรอ IT และข้อมูลของแต่ละบริษัท/สาขาในเครือ Pooilgroup ไม่ปนกัน

**Success metric ที่แนะนำ (BA เสนอ, ยังไม่มี baseline วันนี้):** เก็บตัวเลข 2 ค่าก่อนเริ่มสร้าง แล้ววัดซ้ำ 2 สัปดาห์หลัง deploy —
1. จำนวนครั้ง/เดือนที่พนักงานแจ้งว่า "หาเอกสารไม่เจอ" หรือ "ไฟล์เอกสารผิดที่ต้องขอ IT แก้"
2. เวลาเฉลี่ยที่ใช้หาเอกสาร 1 ชิ้น (ประมาณจากพนักงาน 2-3 คน)

**Definition of Done:** ครบทั้ง 6 scope item ตามที่ล็อกไว้ด้านล่าง + migration เอกสารเก่าผ่านแล้วไม่มีเอกสารตกหล่น (verified count 100%)

## 2. 👥 Panel & Stakeholders

12 seats: PM · BA · SA · Architect · Senior Programmer · UX Designer · UI Designer · QA/QC · Project Owner · Domain Expert (ผู้เชี่ยวชาญการจัดการเอกสาร/ธุรการสำนักงาน) · End User (ธุรการหน้าร้าน) · Devil's Advocate

Round 2 — 3 targeted judges (ไม่ใช่ full 12-seat rerun เพราะ R1 มีข้อขัดแย้งที่ bounded ชัดเจนแค่ 3 เรื่อง): Architecture Judge (fork vs display-filter) · Design Synthesizer (folder design) · Migration & Sequencing Synthesizer

## 3. 🗣️ Debate Highlights (สิ่งที่ทีมเถียงกัน)

**เถียงกันเรื่องที่ 1 — แยกโครงสร้างสาขา/บริษัทแบบไหน:** SA/Architect/PM/Senior Programmer/QA-QC เสนอ fork เต็มรูปแบบ (ย้ายข้อมูลเก่าทั้งหมด) ตั้งแต่ R1 — Devil's Advocate ท้าว่าทำไมไม่ทำแค่กรองที่หน้าจอ (display filter) เพราะเสี่ยงน้อยกว่ามาก **ข้อเท็จจริงที่พลิกเกม:** ตรวจ schema จริงพบว่า `DocumentOwnership.companyId/branchId` เป็นแค่ column UUID เปล่า ไม่มี foreign key ผูกกับตาราง Company/Branch เลย — แปลว่า "fork" ไม่ต้องแตะ schema เดิมเลยถ้าทำแค่ฝั่งสร้างใหม่ **ข้อสรุป:** ไม่ต้อง fork ทั้งหมดและไม่ใช่แค่กรองหน้าจอ — ทำ **hybrid**: ปิดช่องที่ปุ่ม "สร้างสาขา" ของ DocuFlow เขียนข้อมูลเข้าตารางกลางที่ใช้ร่วมกับโปรแกรมอื่น (เจอว่าเขียน live จริงอยู่ตอนนี้ — คือจุดรั่วตัวจริง) เอกสารเก่ายังอ่านจากตารางเดิมได้ตามปกติ

**เถียงกันเรื่องที่ 2 — "โฟลเดอร์" ควรเป็นของใหม่หรือต่อยอดของเดิม:** SA เสนอสร้างตาราง Folder ใหม่แยกจาก DocumentGroup — Domain Expert/Architect/PM/Devil's Advocate (4 เสียงอิสระ ไม่เห็นกัน) ลงเอยตรงกันว่าต้องต่อยอด DocumentGroup เดิม ไม่สร้างระบบจัดหมวดที่ 4 **ข้อสรุป:** ตรวจ schema จริงยืนยันว่า DocumentGroup เหมาะกับการต่อยอด (เอกสาร 1 ชิ้นอยู่ grup เดียวอยู่แล้วตามโครงสร้างข้อมูลปัจจุบัน) — เพิ่ม parentGroupId แทนสร้างตารางใหม่

**เถียงกันเรื่องที่ 3 — ลากวางจริงหรือปุ่มกด:** CEO ขอ "ลากวาง" ตรงๆ — UX Designer, UI Designer, End User (คนละมุมมอง ไม่เห็นกัน) ลงเอยตรงกันว่าลากจริงบนมือถือจะพลาดบ่อย (ชนกับการ scroll) **ข้อสรุป:** ใช้ปุ่ม "ย้ายไปที่..." เป็นหลัก ไม่ใช่ลากวาง — คงไว้ตามเจตนาเดิม (ย้ายของได้) แค่เปลี่ยนวิธีกด

**เถียงกันเรื่องที่ 4 — migrate ข้อมูลเก่ายังไง:** SA/Architect/QA-QC อยากย้ายครั้งเดียวจบ (cutover) — Senior Programmer อยากค่อยๆ ย้าย (dual-read ของเก่าไม่ต้องรีบ) **ข้อสรุป:** ใช้ cutover ครั้งเดียว (ปลอดภัยกว่าถ้า verify ครบ) แต่เก็บของเดิมไว้เป็น safety net 1-2 sprint ก่อนลบจริง — เหตุผลที่ไม่เลือก dual-read แบบไม่มีกำหนด: โปรเจกต์นี้เคยเลื่อนงานใหญ่แบบนี้มาแล้ว 2 รอบด้วยข้ออ้าง "ทำทีหลัง" ที่ไม่เคยเกิดขึ้นจริง

## 4. ✅ Consensus Decisions

- **Company/Branch:** สร้างตาราง `DocuflowCompany`/`DocuflowBranch` ใหม่ มี RLS policy ตั้งแต่วันแรก — ใช้เฉพาะตอนสร้างใหม่ (ปุ่ม "สร้างสาขา/บริษัท" ในหน้า settings DocuFlow ชี้มาที่นี่แทน) เอกสารเก่ายังอ่านจากตารางกลางเดิมได้ปกติ ไม่บังคับ migrate ทันที
- **Folder = DocumentGroup ต่อยอด:** เพิ่ม `parentGroupId` (nullable, self-relation) บน DocumentGroup เดิม จำกัดซ้อนได้ **2 ชั้น** (รอ CEO ยืนยัน — ดู Section 7) ย้าย CATEGORIES 8 ปุ่ม hardcode เข้าเป็น DocumentGroup top-level จริงในฐานข้อมูล เลิกใช้ array คงที่
- **ย้ายเอกสาร (#5):** UPDATE แถว DocumentOwnership เดิม (level='group') ไม่สร้างแถวซ้ำ + เก็บ audit log แยกตาราง (ใคร/จาก/ไป/เมื่อไหร่) ทุกครั้งที่ย้าย ทำในปุ่ม "ย้ายไปที่..." เดียวกับที่ใช้ migrate เอกสารเก่า (พนักงานเห็น+ยืนยันเอง กันตื่นตระหนกว่าเอกสารหาย)
- **Tag (#4):** ยังพิมพ์ tag ใหม่ได้ (ไม่ปิดเด็ดขาด) แต่แยกเป็นปุ่ม "+ เพิ่ม tag ใหม่" ชัดเจน ไม่ใช่กด Enter เนียนๆ เหมือนเดิม — ข้อมูลที่โชว์เป็น dropdown อยู่แล้วถูกต้อง (org-scoped เฉพาะของจริงที่เคยสร้าง)
- **กลุ่มเอกสารด่วน (#3):** ดึง dialog ที่มีอยู่แล้วในฟอร์ม upload มาติดซ้ำบนหน้า list เอกสาร ไม่สร้างใหม่
- **ค่าใช้จ่าย (#6):** amount (Decimal ไม่ใช่ float) + ชื่อรายการ + ความถี่ (รายเดือน/รายปี/ครั้งเดียว) ตาม spec ที่ CEO ให้ไว้ตรงๆ — เป็น section ที่พับเก็บ ("เพิ่มข้อมูลค่าใช้จ่าย ถ้ามี") ไม่บังคับกรอก มี label เตือนว่าเป็นข้อมูลอ้างอิงในเอกสาร ไม่ใช่ตัวเลขบัญชีจริง (ป้องกันเข้าใจผิดว่า sync กับ Ledger)
- **RLS:** ตารางใหม่ทุกตัว (DocuflowCompany/Branch) ต้องมี RLS policy อยู่ใน migration เดียวกับตอนสร้างตาราง ไม่แยกทำทีหลัง — ไม่ว่า CEO จะตอบ Section 7 ข้อ 3 ยังไง

## 5. 🔗 Integration Map

- **Shared data:** `Company`/`Branch` กลาง (ใช้ร่วมกับ ClawFleet/Ledger/ChairOps/ซ่อมบำรุง) — DocuFlow หยุดเขียนเข้าตารางนี้ แต่ยังอ่านได้สำหรับเอกสารเก่า ไม่กระทบโปรแกรมอื่นเลย
- **Security audit คู่ขนาน:** DocuFlow ถูก audit แยกตีว่า "แดง" เรื่อง RLS บน `company_id` — งานนี้ไม่ทำให้ปัญหานั้นดีขึ้นหรือแย่ลง (คนละตารางกัน) แต่ตารางใหม่ของงานนี้ต้องไม่สร้างปัญหาเดียวกันซ้ำ (จึงล็อก RLS-day-1 เป็นเงื่อนไขที่ไม่ต่อรอง)
- **AI metadata extraction ที่มีอยู่แล้ว:** ใช้ช่วย suggest กลุ่มให้เอกสารเก่าตอน migrate (พนักงาน confirm เป็น batch แทนจัดเองทีละไฟล์)
- **Reuse:** DocumentGroup quick-create dialog, upload form Field/Input/Dialog primitives, signer-picker combobox pattern (เพิ่ง ship ในเซ็นเอกสาร) — ไม่สร้าง component ใหม่ซ้ำ

## 6. 🧩 Feature Spec (MoSCoW)

**Must:** #3 quick-create shortcut, #4 tag dropdown+explicit-add, #6 cost field, DocuflowCompany/Branch write-path + RLS, DocumentGroup nesting (2 ชั้น), #5 move document + audit log, migrate CATEGORIES เข้า DocumentGroup

**Should:** AI-assisted group suggestion สำหรับ migrate เอกสารเก่า, notice แจ้งพนักงานล่วงหน้าก่อน cutover

**Could:** native drag-and-drop บน desktop (progressive enhancement, ไม่ใช่ baseline), summary view ค่าใช้จ่ายรวม

**Won't (รอบนี้):** เชื่อม cost field เข้า Ledger/CashHub, ซ้อนโฟลเดอร์เกิน 2 ชั้น (เว้นแต่ CEO ยืนยันใน Section 7), multi-group ต่อเอกสาร (ยังเป็น exclusive placement)

## 8. ⚠️ Risks (Top 5)

1. เอกสารเก่าที่ migrate ผิด mapping อาจหาไม่เจอชั่วคราว — คุมด้วย dry-run count verify 100% ก่อน cutover จริง
2. สาขาที่ DocuFlow เคยสร้างเข้าตารางกลางไปแล้วในอดีต อาจมีโปรแกรมอื่นใช้งานอยู่จริง (ดู Section 7 คำถาม 2)
3. ซ้อนโฟลเดอร์ 2 ชั้นอาจไม่พอสำหรับบางการใช้งานในอนาคต — ขยับเพิ่มทีหลังง่ายกว่าลดทีหลัง
4. งาน migration ที่เก็บของเดิมไว้ "ชั่วคราว" อาจกลายเป็นค้างถาวรถ้าไม่ตั้งเส้นตาย (ประวัติโปรเจกต์นี้เคยเกิดแบบนี้มาแล้ว) — ต้องตั้ง ticket ลบของเก่าไว้ในปฏิทินตั้งแต่วัน cutover
5. โมดูลนี้เพิ่งเจอ production-only bug (import chain, pdf-parse) วันนี้เอง — ฟีเจอร์ใหม่ที่ดึง dependency ใหม่ต้องเทส production build จริง ไม่ใช่แค่ dev server
