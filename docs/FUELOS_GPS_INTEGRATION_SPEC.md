# 🛰️ FuelOS × GPS — Integration Spec Sheet (เอกสารสำหรับคุยกับผู้ให้บริการ GPS)

> **เวอร์ชัน:** 1.0 · วันที่ 2026-06-01
> **เจ้าของระบบ:** Pooil Group (PO Oil) — ธุรกิจขายส่งน้ำมัน
> **ผู้รับเอกสาร:** ทีมเทคนิคของผู้ให้บริการระบบ GPS (GPS Vendor)
> **วัตถุประสงค์:** เชื่อมข้อมูลตำแหน่งรถบรรทุกน้ำมัน เข้าสู่โปรแกรมจัดการขายส่งน้ำมันภายในของบริษัท (เพื่อให้ฝ่ายขาย + ฝ่ายจัดส่งเห็นตำแหน่งรถ real-time)

---

## 0. สรุปสำหรับผู้บริหาร (อ่าน 30 วินาที)

บริษัทกำลังสร้าง **โปรแกรมภายในสำหรับฝ่ายขายน้ำมัน** ที่ต้องแสดง **ตำแหน่งรถบรรทุกแบบ real-time** บนแผนที่ + สถานะการจัดส่ง
เราทราบว่าผู้ให้บริการมีข้อมูลนี้อยู่แล้ว (ส่งเข้ากรมการขนส่งทางบกตามกฎหมายอยู่ทุกวัน) และแจ้งว่า**มีให้เราเชื่อมได้ทั้ง 2 รูปแบบ**

เอกสารนี้คือ:
1. **คำถามที่เราขอคำตอบ** จากผู้ให้บริการ (ส่วนที่ 2–3)
2. **สิ่งที่เราอยากให้ผู้ให้บริการเตรียม/ส่งมอบ** (ส่วนที่ 4)
3. **สิ่งที่ฝั่งเราจะเตรียมเอง** (ส่วนที่ 5)
4. **รายการข้อมูล (data fields) ที่เราต้องการ** (ส่วนที่ 6)

---

## 1. รูปแบบการเชื่อมต่อ 2 แบบ + แบบที่เราเลือก

| | **แบบ A · Pull (เราดึงเอา)** ⭐ **เลือกแบบนี้** | **แบบ B · Push (ผู้ให้บริการยิงมา)** |
|---|---|---|
| ทิศทางข้อมูล | โปรแกรมเรา → เรียก API ของผู้ให้บริการเป็นรอบ ๆ → ได้ตำแหน่งรถกลับมา | กล่อง GPS → server ผู้ให้บริการ → ยิงเข้า endpoint ของเรา (รูปแบบเดียวกับที่ส่งกรมขนส่ง) |
| ใครสร้างปลายทาง | ผู้ให้บริการมี API อยู่แล้ว เราแค่เรียก | เราต้องสร้าง endpoint รับ + ออก credential ให้ผู้ให้บริการ |
| ความปลอดภัย | สูง (เราเป็นฝ่ายเรียก ไม่เปิด public endpoint) | ต้องป้องกัน endpoint + จำกัด IP |
| ความเหมาะกับงานเรา | ✅ เหมาะสุด — "รถอยู่ไหนตอนนี้ + ส่งถึงรึยัง" | เก็บ track ละเอียดทั้งวัน (เกินจำเป็นช่วงแรก) |

> **การตัดสินใจของเรา:** ใช้ **แบบ A (Pull)** เป็นหลัก
> เอกสารส่วนที่ 2 จึงเน้นรายละเอียดของแบบ A · ส่วนที่ 3 เป็นคำถามของแบบ B (เผื่อใช้ภายหลัง)
>
> 👉 **คำถามข้อแรกสุดที่อยากให้ผู้ให้บริการยืนยัน:** บริษัทรองรับการให้เราดึงข้อมูล (Pull API) ได้ใช่หรือไม่? ถ้าใช่ ขอดำเนินการตามส่วนที่ 2

---

## 2. คำถามหลัก — แบบ A (Pull API) ที่เราจะใช้

### 2.1 ปลายทาง (Endpoint) และวิธีเรียก
1. **Base URL / Endpoint** ของ API ดู "ตำแหน่ง + สถานะรถ real-time" คืออะไร? (เช่น `https://api.gpsvendor.co.th/v1/vehicles/positions`)
2. เป็น **REST API** (HTTP GET/POST + JSON) ใช่ไหม? ถ้าไม่ใช่ ใช้รูปแบบอะไร (SOAP / WebSocket / อื่น ๆ)?
3. ขอ **เอกสาร API (API Documentation)** ฉบับเต็ม + **ตัวอย่าง Request และ Response จริง (sample JSON)**
4. เรียกครั้งเดียวได้ **ตำแหน่งรถทุกคัน** เลยไหม หรือต้องเรียกทีละคัน (per `unit_id` / per ทะเบียน)?

### 2.2 การยืนยันตัวตน (Authentication)
5. ใช้กุญแจแบบไหน — **API Key / Bearer Token / OAuth / Username-Password (Basic Auth)**?
6. ขอ **บัญชีทดสอบ (Test/Sandbox Account) + API Key สำหรับทดสอบ** เพื่อให้เราต่อระบบลองได้ก่อนใช้จริง
7. Token/Key มี **วันหมดอายุ** ไหม? ถ้ามี ต้องต่ออายุ (refresh) อย่างไร?

### 2.3 ข้อจำกัดการเรียก (Rate Limit / IP)
8. เรียกดูได้ **บ่อยแค่ไหน** — ทุกกี่วินาที/นาที? (เราอยากได้ความถี่ ~ทุก 15–30 วินาที)
9. มี **จำกัดจำนวนครั้งต่อนาที (rate limit)** ไหม? เท่าไหร่?
10. ต้อง **แจ้ง IP Address ของเราล่วงหน้า (IP Whitelist)** ก่อนเรียกได้ไหม? (ถ้าใช่ เราจะแจ้ง IP ให้)

### 2.4 ข้อมูลที่ได้กลับมา (Response Fields)
11. Response มี field อะไรบ้าง? เราต้องการอย่างน้อยตามตารางใน**ส่วนที่ 6** (พิกัด ความเร็ว เครื่องติด/ดับ ทิศทาง เวลาอัปเดตล่าสุด ฯลฯ)
12. **เวลา (timestamp)** ที่ส่งมาเป็น **UTC (ISO 8601)** หรือเวลาไทย? มี field "เวลาอัปเดตล่าสุดของรถคันนี้" ไหม?
13. ถ้ารถ **จอด/ดับเครื่อง/สัญญาณขาด** ข้อมูลจะแสดงอย่างไร (ส่งตำแหน่งล่าสุด หรือไม่ส่ง)?

### 2.5 ข้อมูลย้อนหลัง (Historical — ถ้ามี)
14. มี API **ดูเส้นทางย้อนหลัง** (เช่น เส้นทางรถเมื่อวาน / ช่วงเวลาที่ระบุ) ไหม? ขอ endpoint + เอกสารด้วย (ไว้ทำรายงาน/ยืนยันการส่ง)

---

## 3. คำถามสำรอง — แบบ B (Push) เผื่อใช้ภายหลัง

> ตอบเฉพาะถ้าผู้ให้บริการแนะนำแบบ B หรือเราตัดสินใจใช้ในอนาคต

15. ผู้ให้บริการยิงข้อมูลมาที่ endpoint ของเราในรูปแบบ **มาตรฐานกรมขนส่ง (DLT JSON)** ตรง ๆ เลยใช่ไหม?
16. ยิงมา **ทุกกี่นาที** และ **กี่คันต่อครั้ง**?
17. ฝั่งผู้ให้บริการต้องการอะไรจากเราบ้าง — **URL ปลายทาง, Username/Password, IP ของเรา**?
18. ถ้า server เราล่มชั่วคราว มีระบบ **ส่งซ้ำ/ส่งย้อนหลัง (backup/retry)** ไหม?

## 4. ✅ สิ่งที่อยากให้ "ผู้ให้บริการ" เตรียม/ส่งมอบ (Deliverables Checklist)

ขอรบกวนผู้ให้บริการเตรียมสิ่งเหล่านี้ เพื่อให้เราเริ่มเชื่อมระบบได้:

- [ ] **เอกสาร API (API Documentation)** ของ Pull API + คำอธิบาย field ทุกตัว
- [ ] **ตัวอย่างข้อมูลจริง (sample Request/Response JSON)** อย่างน้อย 1 ชุด
- [ ] **บัญชีทดสอบ + API Key/Token สำหรับทดสอบ (sandbox)**
- [ ] **Base URL** ของระบบทดสอบ และระบบจริง (production)
- [ ] **รายการรถทั้งหมดของเราในระบบ** — ตาราง: `เลขทะเบียนรถ` ↔ `เลขกล่อง GPS (unit_id)` ↔ `รุ่นกล่อง` (ดูส่วนที่ 5.2 ว่าทำไมสำคัญ)
- [ ] **ข้อจำกัดการใช้งาน** — ความถี่เรียกได้, rate limit, ต้อง whitelist IP ไหม
- [ ] **ค่าใช้จ่าย** (ถ้ามี) สำหรับการใช้ API
- [ ] **ช่องทางติดต่อทีมเทคนิค** (อีเมล/เบอร์/LINE) กรณีเชื่อมแล้วติดปัญหา

## 5. 🔧 สิ่งที่ "ฝั่งเรา" ต้องเตรียม (Internal Checklist)

### 5.1 ระบบ (โปรแกรมเมอร์ฝั่งเรา)
- [ ] **ตัวเรียก API (API client)** ดึงตำแหน่งรถจากผู้ให้บริการ
- [ ] **งานเบื้องหลังดึงข้อมูลเป็นรอบ (polling job)** ทุก ~15–30 วินาที (ปรับตาม rate limit ของผู้ให้บริการ)
- [ ] **ที่เก็บข้อมูลตำแหน่ง** — ตาราง `driver_locations` (มีอยู่แล้วในระบบ) + ปรับให้ผูกกับ "กล่อง/รถ" แทน "คนขับ"
- [ ] **ตารางจับคู่ "เลขกล่อง GPS (unit_id) ↔ รถของเรา (Truck)"** — สำคัญมาก (ดู 5.2)
- [ ] **หน้าจอแผนที่ real-time** แสดงตำแหน่งรถ + สถานะ (เครื่องติด/ดับ, ความเร็ว, เวลาอัปเดตล่าสุด)
- [ ] เก็บ **API Key อย่างปลอดภัย** ใน environment variable (ไม่ commit ลงโค้ด)

### 5.2 ⭐ การจับคู่รถ (ต้องทำให้ครบก่อนใช้จริง)
ข้อมูล GPS อ้างอิง **เลขกล่อง (`unit_id`, 27 ตัวอักษร)** และ **เลขทะเบียนรถ** — แต่ระบบเราอ้างอิงรถเป็น "คันที่ X"
ดังนั้นต้องมี **ตารางจับคู่** ว่า กล่องเลขไหน = รถคันไหนของเรา → จึงต้องขอ "รายการรถ + unit_id" จากผู้ให้บริการ (ส่วนที่ 4)

### 5.3 ข้อมูลที่เราต้องเตรียมส่งให้ผู้ให้บริการ
- [ ] **IP Address (สาธารณะ)** ของ server เรา — กรณีต้อง whitelist
- [ ] (ถ้าใช้แบบ B) **URL ปลายทาง + Username/Password** ที่เราออกให้ผู้ให้บริการ

### 5.4 การตัดสินใจที่ CEO ต้องเคาะ
- [ ] **ความถี่อัปเดต** ที่ยอมรับได้ (เราเสนอ ~15–30 วินาที — สดพอสำหรับติดตามรถส่งของ)
- [ ] เก็บข้อมูลตำแหน่ง **ย้อนหลังกี่วัน** (เช่น 30/90 วัน) — กระทบขนาดฐานข้อมูล

## 6. 📋 รายการข้อมูล (Data Fields) ที่เราต้องการ

อ้างอิงจากมาตรฐานกรมขนส่งทางบก (DLT) — เพื่อให้ผู้ให้บริการเทียบได้ว่า Pull API มี field เหล่านี้ครบไหม

| ลำดับความสำคัญ | Field (มาตรฐาน DLT) | ความหมาย | ใช้ทำอะไรในโปรแกรมเรา |
|---|---|---|---|
| 🔴 ต้องมี | `unit_id` | เลขกล่อง GPS | จับคู่ว่าเป็นรถคันไหน |
| 🔴 ต้องมี | `lat`, `lon` | พิกัด (ละติจูด/ลองจิจูด) | ปักหมุดบนแผนที่ |
| 🔴 ต้องมี | `utc_ts` | เวลาที่กล่องส่งข้อมูล | รู้ว่าตำแหน่งนี้สดแค่ไหน |
| 🔴 ต้องมี | `speed` | ความเร็ว (กม./ชม.) | รถวิ่ง/จอด, ขับเร็วเกินไหม |
| 🔴 ต้องมี | `engine_status` | เครื่องยนต์ ติด(1)/ดับ(0) | รถกำลังทำงานหรือจอด |
| 🟡 อยากได้ | `course` | ทิศทางการวิ่ง (0–360°) | หัวรถหันไปทางไหน (ลูกศรบนแผนที่) |
| 🟡 อยากได้ | `vehicle_id` / ทะเบียนรถ | เลขทะเบียน | จับคู่/แสดงผลให้คนอ่านง่าย |
| 🟡 อยากได้ | `fix` | สถานะสัญญาณ GPS | บอกว่าพิกัดเชื่อถือได้ไหม |
| 🟡 อยากได้ | `mileage` | เลขไมล์สะสม (เมตร) | ดูระยะทางที่วิ่ง |
| 🟢 มีก็ดี | `ext_power_status` | สถานะไฟเลี้ยง (ถูกถอดกล่องไหม) | แจ้งเตือนกล่องถูกถอด |
| 🟢 มีก็ดี | `over_speed_count` | จำนวนครั้งขับเกินกำหนด | ความปลอดภัยคนขับ |
| 🟢 มีก็ดี | `driver_id` | รหัสใบขับขี่ (ถ้ารูดบัตร) | รู้ว่าใครขับ |

> หมายเหตุ: ถ้า Pull API ใช้ชื่อ field ต่างจากนี้ ขอแค่ผู้ให้บริการระบุว่า field ไหน = ความหมายไหน (mapping) ก็พอ

## ภาคผนวก — ข้อมูลทางเทคนิคจากมาตรฐาน DLT (อ้างอิง)

เผื่อทีมเทคนิคผู้ให้บริการต้องการเทียบกับสิ่งที่ส่งกรมขนส่งอยู่แล้ว:

- รูปแบบข้อมูล: REST + JSON (UTF-8)
- โครงสร้าง JSON: `{ "vender_id": int, "locations_count": int, "locations": [ { unit_id, driver_id, seq, utc_ts, recv_utc_ts, lat, lon, alt, speed, engine_status, fix, license, course, hdop, num_sats, gsm_*, mileage, ext_power_status, ext_power, high_acc_count, high_de_acc_count, over_speed_count, max_speed } ] }`
- พิกัด: ทศนิยมอย่างน้อย 5 ตำแหน่ง
- เวลา: UTC ISO 8601 (เช่น `2016-01-07T22:13:56.504Z`)
- (แบบ B) Auth: Basic Authentication = `base64(username:password)` ใน HTTP Header `Authorization: Basic <hash>`
- (แบบ B) Endpoint แนว DLT: `POST /gps/add/locations`, ตอบกลับ `{ "code":1, "message":"ok", "received_records":N }`
