## 1. 🎯 Goal & Success Metrics

**เป้าหมายธุรกิจ:** ทุกแม่บ้าน (ใหม่และเก่าที่ยังไม่เซ็น) มีสัญญาจ้างเหมาทำความสะอาด+เก็บเงินที่เซ็นถูกต้องตามกฎหมาย พร้อมข้อมูลยืนยันตัวตน (บัตร ปชช./เซลฟี่), ที่ทำงานปัจจุบัน, เบอร์ฉุกเฉิน 2 คน, เลขบัญชีธนาคาร — ครบก่อนที่จะปล่อยให้ถือเงินสดลูกค้าจริง

**Success metric (แนะนำ, รอ CEO ยืนยัน):**
- % แม่บ้าน active ที่มีสัญญาเซ็นแล้ว + เอกสารครบ (เทียบ baseline วันนี้)
- เวลาเฉลี่ยจาก "ส่งลิงก์" → "เซ็นเสร็จ"
- จำนวนแม่บ้านเก่าที่ยังไม่เคยเซ็น (backlog) ที่เคลียร์ได้ในเดือนแรก

**Definition of Done (v1):** แอดมินกดจากหน้าแม่บ้าน (คนที่มี login อยู่แล้ว) → ส่งลิงก์สัญญา → แม่บ้านเข้าผ่าน session เดิม (ไม่ต้อง build public/anonymous access ใหม่) → กรอกข้อมูลที่ขาด (เซลฟี่, เบอร์ฉุกเฉินคนที่ 2) → อ่าน+เซ็นสัญญา (สไตล์ RentSpace) → สถานะขึ้นในหน้าแอดมิน

## 3. 🗣️ Debate Highlights — ทีมเถียงกันเรื่องอะไร แล้วลงเอยยังไง

**ประเด็นใหญ่ที่สุด (และเป็นตัวตัดสินงบประมาณทั้งก้อน): ลิงก์นี้ต้อง "เปิดได้โดยไม่ต้อง login" จริงไหม?**

R1 เกือบทุก seat (SA, Programmer, UX, QA/QC, Devil's Advocate) ตีความ brief ตรงตัวว่าต้องสร้าง "public token, ไม่ต้อง login เลย" แบบเดียวกับ RentSpace's sign page — และประเมินว่านี่คืองานก้อนใหญ่ที่สุด (SA เจอว่า `/api/r2/sign` เคยถูกปิดช่อง anonymous upload มาแล้วอย่างจงใจ, Programmer เสนอ spike "mint Supabase session จาก token" 0.5-1 วันก่อนล็อกแผน, PM ประเมิน 8-11 วัน โดยอ้างอิง Recruit workshop ที่บานจาก 3-4 วัน เป็น 14-16 วันเมื่อเจอปัญหาเดียวกัน)

**Devil's Advocate ตั้งคำถามค้านตรงจุดนี้ตั้งแต่ R1**: "ทำไมต้อง public link ทั้งที่ ChairOps มี LINE-login invite flow ที่ทำงานลื่นอยู่แล้ว (เชิญ→tap→login→ใช้งานได้เลย)? ถ้าไม่มีเหตุผลธุรกิจหนักแน่น จะค้านให้ยกเลิก public-link แนวทางทั้งหมด"

**CEO ตอบเองกลางที่ประชุม (ก่อน Round 2 จะเริ่ม) — ยืนยันแนวทางของ Devil's Advocate ตรงๆ:**
> "เราจะส่งจากหน้าแม่บ้านเดิมในระบบ — แม่บ้านสาขานั้นเค้ามี login ได้อยู่แล้ว ส่งลิงก์สัญญาไปสำหรับแม่บ้านคนนั้นเลย ถ้าเป็นพนักงานใหม่ ให้ส่งลิงก์เชิญพนักงานเก้าอี้นวด แล้วกรอก แล้วให้ทำสัญญาตัวนี้ต่อเลย"
> "ใช้แค่เก้าอี้นวดพอ" (ไม่ต้องใช้ร่วมกับ Recruit)

**ผลคือข้อถกเถียงที่แพงที่สุดในห้องถูกปิดจบด้วยข้อเท็จจริงเดียว: ไม่ต้องสร้าง public/anonymous access เลย** ทั้ง 2 กลุ่มเป้าหมายมี auth path ที่มีอยู่แล้วในระบบ:
- แม่บ้านเก่าที่มี login อยู่แล้ว → ใช้ session เดิมตรงๆ
- พนักงานใหม่ → ใช้ลิงก์เชิญ (`createMaidInvite`, LINE-login) ที่มีอยู่แล้ว แล้วต่อเข้าสัญญาทันทีหลัง onboarding

นี่ตัดงานที่แพงที่สุด (token wrapper ใหม่, upload route ใหม่, rate-limiting สำหรับ anonymous access, TTL design, session-mint spike) ออกไปทั้งก้อน — เหลืองานจริงที่เล็กกว่ามาก (ดู §6)

**ประเด็นรองที่ยังจริงอยู่แม้ auth model จะเปลี่ยน (ไม่ถูกกระทบจากคำตอบของ CEO):**
- **PDPA/กฎหมายแรงงาน (Domain Expert, unanimous กับ Devil's Advocate)**: สัญญาเรียกแม่บ้านว่า "ผู้รับจ้าง" แต่มีลักษณะควบคุมแบบลูกจ้าง (กำหนดเวลาทำงาน, บทลงโทษ, ต่ออายุอัตโนมัติ) — พ.ร.บ.คุ้มครองแรงงาน ม.5 ดูพฤติการณ์จริงไม่ใช่ชื่อสัญญา — ความเสี่ยงนี้**ไม่เกี่ยวกับว่าใช้ auth แบบไหน** ยังต้องแก้ก่อน ship
- **รูปบัตร ปชช. มีช่อง "ศาสนา" ติดมา** = ข้อมูลอ่อนไหวพิเศษ PDPA ม.26 ต้องขอ consent แยก (ยืนยันซ้ำจาก Recruit workshop 2 วันก่อน)
- **ข้อ 3 "ชดใช้เต็มจำนวนไม่มีเงื่อนไข"** เสี่ยงศาลลดทอน/เพิกถอนตาม ป.พ.พ.ม.383 + พ.ร.บ.ข้อสัญญาไม่เป็นธรรม ม.4
- UI/UX (UX, UI, End User): หน้าเดียว scroll ยาว ไม่ทำ wizard หลายหน้า — ยืนยันจาก pattern ที่มีอยู่แล้วทั้งฝั่ง onboarding form เดิมและ RentSpace's sign page

## 4. ✅ Consensus Decisions

1. **Auth: ไม่สร้าง public/anonymous link ใหม่** — แม่บ้านเก่าใช้ session login เดิม, แม่บ้านใหม่ใช้ลิงก์เชิญ LINE-login เดิม (`createMaidInvite`) แล้วต่อเข้าสัญญาทันที
2. **ขอบเขต: ChairOps เท่านั้น** — ไม่ทำ shared capability กับ Recruit (CEO ยืนยันตรง "ใช้แค่เก้าอี้นวดพอ")
3. **สัญญาที่ใช้จริง = ฉบับที่มีอยู่แล้ว** ("สัญญาจ้างเหมาทำความสะอาดและเก็บเงินนำส่งธนาคาร") ไม่ใช่สัญญาจ้างแรงงานแบบทดลองงานที่ส่งผิดตอนแรก
4. **ดีไซน์: ยืมสไตล์ RentSpace ตรงๆ** (import `.rs-scope` token) ไม่สร้างสีใหม่ ไม่มีไฟล์โลโก้แยก (v1) — เนื้อหาสัญญา 5 ข้อคงเดิมทุกตัวอักษร ห้ามแก้ในนามดีไซน์
5. **Data model**: เพิ่ม emergency contact คนที่ 2 (columns คู่ที่ 2 บน `ChairopsUser`, ไม่ต้องแยก table), เพิ่ม selfie field — ทั้งคู่เป็น additive/nullable migration
6. **Selfie**: reuse `components/playland/face-capture.tsx` (มีอยู่แล้ว) แต่ต้องเขียนใหม่ให้เก็บรูปขึ้น R2 จริง (ปัจจุบันถ่ายแล้วทิ้ง)
7. **สัญญา 5 ข้อต้องผ่านทนายตรวจก่อน ship ระบบเซ็นออนไลน์** — ไม่ใช่ nice-to-have (unanimous: Domain Expert + Devil's Advocate)

## 5. 🔗 Integration Map

- **Reuse หลัก**: `app/(admin)/chairops/(maid)/m/contract` (fill→preview→เซ็นลายเซ็น, มี IP/UA/SHA-256 hash audit อยู่แล้ว) + `app/(admin)/chairops/(maid-public)/m/onboarding` (เก็บ phone/emergency/workplace/bank/ID เกือบครบแล้ว) — ทั้งคู่ session-gated อยู่แล้ว ตรงกับที่ CEO ยืนยัน ไม่ต้องแก้ auth model
- **เชื่อมสองหน้าเป็น flow เดียว** สำหรับพนักงานใหม่: onboarding เสร็จ → ต่อเข้า contract sign ทันที (ปัจจุบันเป็น 2 หน้าแยก ไม่เชื่อมกัน)
- **เพิ่มปุ่ม "ส่งลิงก์สัญญา" ในหน้าแม่บ้าน (office view)** สำหรับแม่บ้านเก่าที่ login อยู่แล้ว — ส่งเป็น LINE message หรือคัดลอกลิงก์ตรงไปหน้า `/m/contract`
- **ดีไซน์**: import `components/rentspace/tokens.css` (`.rs-scope`) เข้าไฟล์หน้าเซ็นสัญญาแม่บ้าน — cross-module CSS dependency ใหม่ (ChairOps→RentSpace) ที่ไม่เคยมีมาก่อน ต้อง SA/Architect รับทราบ
- **ไม่แตะ**: `/api/r2/sign` (คงมาตรฐาน login-only ตามที่ปิดช่องไว้แล้ว), DocuFlow's `SignerInterface` (คนละ mechanism), RentSpace's token/security pattern (ไม่มี TTL/rate-limit — ยืมแค่สไตล์ ไม่ยืม implementation)
- **Migration**: `ChairopsUser` เพิ่ม emergencyContact2/emergencyPhone2 + selfieImageUrl/selfieCapturedAt (additive nullable)

## 6. 🧩 Feature Spec (MoSCoW)

**Must (v1):**
- ปุ่ม "ส่งลิงก์สัญญา" ในหน้าแม่บ้าน (office) สำหรับแม่บ้านที่ login อยู่แล้ว
- เชื่อม onboarding→contract เป็น flow เดียวสำหรับพนักงานใหม่
- เพิ่ม selfie capture (reuse FaceCapture + เขียนใหม่ให้เก็บ R2 จริง)
- เพิ่ม emergency contact คนที่ 2 (migration + form + admin view)
- Restyle หน้าเซ็นสัญญาด้วย RentSpace's `.rs-scope`
- ทนายตรวจเนื้อหาสัญญา 5 ข้อ ก่อน launch (การจำแนกจ้างเหมา/จ้างแรงงาน, ข้อ 3 ชดใช้เต็มจำนวน)
- PDPA consent แยกสำหรับข้อมูลอ่อนไหว (บัตร ปชช./เซลฟี่) + mask ช่องศาสนาก่อนบันทึกถ้าเป็นไปได้

**Should:**
- Field-level onboarding status (ไม่ใช่ boolean เดียว) ให้ office เห็นว่าใครเอกสารขาดอะไร
- Consent/แจ้งเตือนเจ้าของเบอร์ฉุกเฉิน (ข้อมูลบุคคลที่สาม)

**Could:**
- โลโก้ JP Sync Group จริง (mechanism มีอยู่แล้วที่ `/settings`, แค่ยังไม่มีไฟล์)
- Manual review queue ก่อนปลดล็อก onboardingComplete

**Won't (v1):**
- Public/anonymous no-login access (ตัดออกตามการยืนยันของ CEO)
- Shared capability กับ Recruit
- Automated ID/selfie verification (OCR/liveness API)

## 7. ❓ Open Questions for CEO

1. **ทนายตรวจสัญญาก่อน ship** — มีทนาย/ที่ปรึกษากฎหมายที่ใช้อยู่แล้วไหม หรือให้ผมช่วยร่างประเด็นที่ต้องถามทนายเป็นข้อๆ (จำแนกจ้างเหมา/จ้างแรงงาน, ข้อ 3 ชดใช้เต็มจำนวน, PDPA consent)?
2. **Selfie เก็บถาวรหรือตรวจสดแล้วทิ้ง** — เก็บเป็นหลักฐานถาวร (ต้องมี consent+retention policy) หรือแค่ให้ office เปิดดูตอนตรวจครั้งแรกแล้วลบ?
3. **v1 ทำครบทีเดียวหรือแบ่งเฟส** — เซลฟี่+เบอร์ฉุกเฉินคนที่ 2 เป็น migration ใหม่ทั้งคู่ ทำพร้อม v1 เลย หรือปล่อย v1 แบบไม่มีเซลฟี่ก่อน (เร็วกว่า) แล้วเพิ่มทีหลัง?
4. **Timeline** — ตอนนี้ scope เล็กลงมากเพราะไม่ต้องสร้าง public-link (ประหยัดงานส่วนที่แพงที่สุดไป) เป้า "1 สัปดาห์" realistic ขึ้นแล้ว แต่ยังต้องรอผลตรวจกฎหมายก่อนล็อก launch date — โอเคไหมถ้าจะ build ฟีเจอร์ให้เสร็จก่อน แล้วรอผลทนายค่อย enable ให้แม่บ้านเซ็นจริง?

## 8. ⚠️ Risks (Top 5)

1. **กฎหมาย**: สัญญาอาจถูกตีความเป็นจ้างแรงงานจริง (ไม่ใช่จ้างทำของ) — กระทบภาระประกันสังคม/ค่าชดเชยย้อนหลังถ้ามีข้อพิพาท
2. **PDPA**: บัตร ปชช.มีช่องศาสนา + เซลฟี่ = ข้อมูลอ่อนไหวพิเศษ ต้อง consent แยกก่อนเก็บ
3. **ข้อสัญญาไม่เป็นธรรม**: ข้อ 3 ชดใช้เต็มจำนวนไม่มีเงื่อนไข เสี่ยงศาลเพิกถอนทั้งข้อ
4. **Data race**: กรอกผ่าน 2 จุด (onboarding เดิม + flow ใหม่) เขียนทับ column เดียวกันแบบ last-write-wins ถ้าไม่ผูก `onboardingComplete` เป็น source of truth เดียว
5. **Cross-module CSS dependency ใหม่** (ChairOps import RentSpace tokens) — ยังไม่เคยมี pattern นี้มาก่อนในเรโป
