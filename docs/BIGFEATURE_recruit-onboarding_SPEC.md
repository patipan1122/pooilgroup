## Goal & Users

- **Feature:** one permanent public link (no login, no expiry, no per-person code) that a newly-confirmed hire uses to submit real personal data, upload ID documents, read the real employment contract, and sign it (drawn signature + live selfie) — replacing a 100% paper onboarding process at PO Oil / JP Sync Group.
- **Who uses:** the new hire (public, unauthenticated, phone-first) · HR/Recruit admin (reviews + approves submissions) · eventually every module that reads `User` (auth-guard implication).
- **Touches:** Recruit (owner) · DocuFlow (signature UI pattern, but see reuse correction below) · ChairOps (Drive-privacy pattern to borrow) · Pool core (`User`, `Company`, login guard).
- **Mode:** new standalone sub-flow of Recruit. **Not** linked to `RecruitApplication`/`RecruitApplicant` — CEO explicitly rejected this twice.
- **Build mode:** Spec + Build — ship real code, verify it, hold production deploy (and specifically "make the public URL live") for a separate explicit CEO go-ahead, per Owner + DevOps recommendation to split those two approvals.

## 🔴 P0 — must fix, not a choice (found by DevilsAdvocate, confirmed independently by SA + QA)

**Reusing the existing `upload-drive` route as originally assumed would make every uploaded ID card and bank book PUBLICLY viewable by anyone with the link.** `lib/recruit/drive.ts`'s `makePublic()` unconditionally sets uploaded files to "anyone with the link, reader" — fine for résumés, catastrophic for national ID photos. A sibling module (ChairOps) hit this exact problem with bank slips and already fixed it (`lib/chairops/storage/drive.ts:270-293`, gated behind `CHAIROPS_DRIVE_PUBLIC_LINKS`, default OFF, with a 2026-06-03 comment explaining the risk). **Build decision: use the ChairOps private-by-default pattern for this feature's Drive integration, not the Recruit one.** This is not optional and not a CEO decision — it's a straightforward "use the already-fixed pattern instead of the already-broken one."

Also confirmed unreusable as-is regardless of privacy: `app/api/recruit/upload-drive/route.ts` hard-requires an `OPEN RecruitJobPosting.slug` to resolve org context — impossible for a standalone, non-slug-based flow. A new route is needed either way; it should be modeled on ChairOps' Drive lib.

## Schema (3 new models, zero FKs into Recruit's applicant pipeline — confirmed deliberate)

```
RecruitOnboardingSubmission
  id, companyId (FK → Company), branchId (nullable FK), positionApplied, desiredStartDate, desiredSalary,
  fullNameTh, fullNameEn, nickname, nationalId (indexed, NOT unique — see dedupe note),
  birthDate, nationality, militaryStatus, phone, lineId, email, maritalStatus,
  addressJson (registered + current), emergencyContactsJson (2), educationJson, workHistoryJson,
  bankName, bankAccountNo, bankAccountName,
  consentTruthful, consentPrivacyRead, consentEmergencyContactNotified (bool, timestamped),
  status (SUBMITTED | HR_REVIEWING | APPROVED | REJECTED), reviewedByUserId, reviewedAt, resultUserId (nullable, set once)
  schemaVersion, answersJson (fallback for anything not in typed columns — mirrors RecruitApplication's own pattern)

RecruitOnboardingDocument
  id, submissionId (FK), docType (id_card|house_reg|bank_book|photo|education|other),
  driveFileId, driveFolderId (private, ChairOps-style — NOT public link)

RecruitOnboardingConsent
  id, submissionId (FK), signedAt, signedIp, signedUserAgent,
  contractContentHash, scrolledToEnd (bool),
  signatureDocId, selfieDocId (plain UUID pointers, not FK — avoids cascade-delete ordering hazard)
```

**Not new-build, reuse as-is:**
- `pending_verification` state → `User.isActive=false` (existing login-guard behavior) + existing `POST /api/admin/users/[id]/reactivate` endpoint, role-gate widened to include the tier that should be able to activate new hires (currently admin-only — confirm with PM whether branch-manager tier should also qualify).
- `employeeCode` → leave `null` at creation, always hand-typed later (no generator exists anywhere in the codebase; don't invent one).
- Company resolution → candidate's company pick in the form maps directly to the real `Company` model (`code: POOIL|JPSYNC`); resolve `companyId` server-side via `Company.findFirst`, never trust a client-sent UUID.

**Genuinely new for this codebase:** this is the **first `prisma.$transaction` usage anywhere in pooilgroup-web** (confirmed — zero existing precedent). The atomic "create `User` + link `resultUserId` + mark submission `APPROVED`" step at HR-approval time needs real care given this project's own incident history with a similar race condition (Drive-folder duplication, 2026-06-07).

## Consistency risks found (not blocking, but must be decided/handled)

1. **Impersonation risk (Customer persona)** — since nothing links a submission to the real hire, someone who knows a new hire's name could submit fake bank details first. No schema fix possible without reopening the "no linking" decision CEO already made twice — mitigation is an **HR SOP**: verify via the phone number used during the actual interview, never the one typed on the form. Will document this in the HR review screen's on-page copy, not enforce it in code.
2. **Camera-only selfie vs. gallery-upload fallback** (UX + PM + QA all independently flagged) — the only ready-made component (`face-capture.tsx`) has a file-upload fallback for when `getUserMedia` is denied/unavailable. A strict "live capture only, no fallback, no exceptions" reading permanently strands candidates on old Android phones or desktop walk-ins, with zero recovery path since there's no reference code for HR to help them resume elsewhere. **Recommendation: keep the existing fallback** (still requires an in-the-moment camera photo when available; falls back to native-camera-app capture, not a gallery picker, when `getUserMedia` isn't supported) rather than build a stricter, riskier version no other module has needed. Flagged to CEO in briefing; defaulting to this unless told otherwise.
3. **No national-ID uniqueness/dedup check exists** — `User` has no national-ID field at all today. Decision: keep `nationalId` indexed but NOT unique on the new submission table (so a legitimate resubmission after a rejected/corrected entry doesn't 500), but flag exact-duplicate national IDs on the HR review screen for manual judgment rather than blocking automatically.
4. **Multi-candidate-per-device localStorage collision** (UX) — since the link has no per-person identifier, two candidates using the same HR tablet back-to-back could load each other's draft. Fix: key the draft by a fresh client-generated `crypto.randomUUID()`, not a shared key, with an explicit "resume previous entry?" prompt only within the same browser session.
5. **"Must scroll to the end" gate is genuinely new UI** (zero prior art anywhere in the codebase) — needs real cross-device testing (iOS rubber-banding, pinch-zoom, font-reflow), not just a desktop check.

## Rollback / kill-switch

New tables are additive-only (safe to drop if abandoned). One DB-backed permanent toggle (not env var, no redeploy needed — none exists yet in this codebase, needs building) gates all three public entry points and renders a "temporarily closed" page instead of erroring, since the URL will already be circulating by the time any kill-switch is needed. The one non-additive touch (login-guard for `isActive=false` new-hire accounts) ships as a strictly no-op early-return for all existing users.

## Deploy sequencing (DevOps)

1. Migration must land in prod **before** any code referencing the new tables (`check-schema-applied.mjs` hard-fails the build otherwise).
2. Split into two separate CEO approvals: (a) merge the code to `setup` — safe, nothing public yet; (b) flip the public URL live — hold until contract-wording legal review (Section 7 of the old workshop doc, items B/C) is resolved.
3. Sentry's existing PII-scrubber already regex-matches Thai ID/phone/email/card numbers — this feature rides on existing monitoring, no new setup needed.
