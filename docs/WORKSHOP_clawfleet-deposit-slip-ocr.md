## 0. 🔑 บริบทที่เปลี่ยนเกมจาก workshop นี้

1. **กลไก "ฝากเงิน" มีอยู่แล้วเต็มรูปแบบ** ที่ `/clawfleet/os/deposits` (`recordCashDeposit()`, `lib/clawfleet/deposit-actions.ts:94`) — ถ่ายรูปสลิป, คำนวณยอดคาดหวัง vs ยอดพิมพ์เอง ±20 บาท, staff ที่ปิดรอบเก็บเงินเอง (`isCustodyHolder`) ใช้ได้อยู่แล้วไม่ใช่ admin-only. **ปัญหาจริงคือหน้านี้ไม่มีลิงก์จากแอปพนักงานเลย** — build 90% ของ requirement ข้อ 1-3 มีอยู่แล้ว งานจริงคือ "เจาะทางเข้าใหม่" ไม่ใช่ "สร้างกลไกใหม่"
2. **`recordCashDeposit()` ต้องการ `sessionIds[]` ที่ผู้ใช้เลือกเอง ไม่ใช่ auto-sum** (verified `deposit-actions.ts:65-69,121-158`) — บังคับให้ต้องมี session-picker (checkbox list จาก `getPendingDeposits()`) ซึ่งตรงกับที่ End User ขอเป๊ะ (กันฝากซ้ำ/ลืมฝาก) โดยบังเอิญเป็นสิ่งที่ระบบเดิมบังคับอยู่แล้ว
3. **AI อ่านสลิปมีของจริงให้ port มาใช้** — ChairOps `extractSlipDetails()`/`checkSlipFraud()` (`lib/chairops/reconcile/slip-ocr.ts`) ทำงานจริงในโปรดักชัน จับโกงจริง 1 เคส (พนักงาน 2 คนใช้สลิปใบเดียวเคลม 2 ครั้งห่างกัน 4 วัน) — แต่เคยพังเงียบ 2 รอบมาก่อน (auth-provider ผิด → null ทุกแถว 2 วันไม่มีใครรู้; Gemini `thinkingBudget` default กิน token จน JSON ขาดกลาง) ต้องเอาบทเรียนทั้ง 2 มาป้องกันซ้ำ
4. **`approvalStatus` เป็น plain String column (ไม่ใช่ DB enum)** ค่าเดิม `NONE/PENDING/APPROVED/REJECTED` — `pushBranchDepositsToLedger` **exclude `PENDING` จากการ push เข้า ledger อยู่แล้ว** (`ledger-push.ts:92-97`) แปลว่า reuse `PENDING` เดิมตรง ๆ สำหรับ "AI ตรวจแล้วต้องรอคนดู" ได้ทันที **ไม่ต้องเพิ่ม enum value ใหม่เลย** — ประหยัดกว่าที่ทีมกลัวไว้ตอนแรกมาก
5. **`PHASES` enum ที่ `/api/clawfleet/upload` เป็น TS array ธรรมดา ไม่ผูก DB** — เพิ่ม `"deposit_slip"` เป็น pure code change ไม่ต้อง migration
6. **`depositedAt` วันนี้แก้ backdate ได้อยู่แล้วแบบไม่มีเพดานเลย** (`deposits-client.tsx:200,220`) — เป็นช่องโหว่เดิมที่มีอยู่ก่อนฟีเจอร์นี้ ไม่ใช่ของใหม่ที่งานนี้เปิดเพิ่ม

## 1. 🎯 Goal & Success Metrics

**เป้าหมายธุรกิจ:** พนักงานเก็บเงินตู้คีบแนบสลิปฝากเงินได้จากหน้าที่ใช้ทุกวันอยู่แล้ว (ประวัติเก็บเงิน) โดยไม่ต้องหาเมนูแยก + เห็นยอดเงินที่เก็บมาแล้วยังไม่ฝากชัดเจน (แยกวันนี้ vs สะสม) + AI ช่วยอ่านยอด/เช็คบัญชีปลายทางกันเงินขาด/เงินเข้าผิดบัญชี + ปิดช่องโหว่สลิปซ้ำแบบที่เคยจับได้จริงใน ChairOps

**Success metrics:**
- **M1:** พนักงานกดแนบสลิป+ฝากเงินจบได้ในหน้าประวัติเก็บเงินหน้าเดียว ไม่ต้องออกจากหน้า ไม่ต้องพิมพ์ยอดเอง (AI prefill ให้ยืนยัน)
- **M2:** ยอด "วันนี้ต้องฝาก" กับ "สะสมทั้งหมดยังไม่ฝาก" โชว์แยกกันชัดบนสุดของหน้า เห็นทันทีไม่ต้องเลื่อน
- **M3:** AI อ่านยอด+ชื่อบัญชีจากสลิปได้จริง (ไม่ null เงียบแบบที่เคยพังใน ChairOps) มี canary แจ้งเตือนถ้าพัง
- **M4:** สลิปซ้ำ/ยอดไม่ตรง/บัญชีไม่ตรง ถูกจับและพักไว้ให้ออฟฟิศตรวจ โดยไม่บล็อกพนักงานจากการฝากเงิน

**Definition of Done:** ครบ M1-M4 + verify จริงกับสลิปจริงอย่างน้อย 8-10 ใบ (ไม่ใช่แค่ build เขียว) + canary ทำงาน + ผ่าน `/verify` เต็ม

## 3. 🗣️ Debate Highlights

- **"เอาของเดิมมาแปะ" vs "สร้างใหม่"** — Architect ฟันธงว่านี่คือ "เพิ่มทางเข้าใหม่ที่เรียกกลไกเดิม" ไม่ใช่ "ย้ายกลไก" — ห้ามแก้ `/clawfleet/os/deposits`/`recordCashDeposit()` ในทางที่เปลี่ยนพฤติกรรมเดิม เพิ่มได้แบบ backward-compatible เท่านั้น ทุกที่นั่งเห็นตรงกัน ไม่มีข้อขัดแย้ง
- **AI auto-fill ยอดหรือไม่** — Senior Programmer/UX/QA/End User/นักบัญชี ทุกคนลงเอยตรงกันเอง (ไม่ต้องมีรอบ 2 ถกเถียง): auto-fill ให้เห็นตัวเลขก่อน พนักงานกดยืนยันเองเสมอ ห้าม auto-submit เงียบ — เหตุผลตรงกัน: AI อ่านสลิปมี error rate ไม่เท่ากับ 0 (แสง/มุม/คุณภาพรูป)
- **บล็อกฝากเมื่อ mismatch หรือแค่ flag** — ทีมสร้างส่วนใหญ่ (Programmer/UX/QA) กลัวการบล็อกจะทำให้พนักงานฝากเงินจริงไม่ได้ ส่วนนักบัญชีอยากบล็อกกรณีชื่อบัญชีไม่ตรง — **แก้ด้วยการแยกชั้น**: ไม่บล็อกการ "ฝาก" (พนักงานส่งได้เสมอ) แต่บล็อกการ "อนุมัติเข้าบัญชีกลาง" (ใช้สถานะ `PENDING` เดิม กันไม่ให้เข้า ledger จนกว่าคนจะตรวจ) — สองฝ่ายพอใจทั้งคู่ ไม่ต้องยกให้ CEO ตัดสิน
- **เพดานวันฝากย้อนหลัง** — นักบัญชี+End User+Devil's Advocate ทั้ง 3 เสียงเตือนตรงกันว่าไม่มีเพดาน = ระบบจับโกงไม่มีความหมาย (คนยักยอกถือเงินไว้นานเท่าไหร่ก็ได้). ทีมเสนอ tiered cap (0-1วัน auto / 2-3วัน ต้องอนุมัติ / >3-7วัน บล็อก) แต่ **CEO ปฏิเสธการจำกัดเวลา** เลือกใช้กลไกอื่นแทน: "ฝากย้อนหลังได้ตลอด แต่ห้ามลบประวัติ อัปโหลดเพิ่มได้อย่างเดียว" — คือใช้ **immutability/audit-trail แทน time-cap** เป็นตัวป้องกัน (append-only) — ยึดตามนี้เป็นการตัดสินสุดท้าย
- **CEO เพิ่มโจทย์ใหม่กลางรอบถาม (narration แบบ W-023 pattern)**: ต้องการเห็นยอด "วันนี้ต้องฝากเท่าไร" แยกจาก "สะสมที่ยังไม่ฝากเท่าไร" เป็นคนละตัวเลข ไม่ใช่ก้อนเดียว
- **Duplicate-check scope** — SA เสนอ scope ตาม `bankAccountId` (แม่นกว่า, สาขาหลายที่ใช้บัญชีร่วมได้), นักบัญชีเสนอ org-wide เผื่อพนักงานย้ายสาขา — สรุป: **เช็คเลขอ้างอิงธนาคาร (ref number) แบบ org-wide ก่อนเสมอ** (ถูก แม่น ไม่มีต้นทุนเพิ่ม เพราะเลขอ้างอิงธนาคารไม่ซ้ำกันข้ามธุรกรรมจริงอยู่แล้ว) **fallback วันที่+ยอดเมื่ออ่าน ref ไม่ได้ ค่อย scope ตาม bankAccountId** (ผ่าน `CfBranchReconcileConfig`) — ดีกว่าทั้ง 2 ข้อเสนอเดิม

## 4. ✅ Consensus Decisions

1. **จุดแนบสลิป** = หน้า "ประวัติเก็บ" (`staff-app-client.tsx` / `HistoryPanel`) โดยตรง ไม่เปิดหน้าใหม่ — เรียก `recordCashDeposit()` เดิมผ่าน inline panel/bottom-sheet
2. **Session picker บังคับ** (ตามที่ฟังก์ชันเดิมต้องการอยู่แล้ว) — ลิสต์รอบเก็บที่ยังไม่ฝาก (ใช้ `getPendingDeposits()` เดิม) ให้พนักงานติ๊กเลือก ไม่ใช่พิมพ์ยอดรวมเอง
3. **โชว์ 2 ตัวเลขแยกกัน**: "วันนี้ต้องฝาก" (sum ของ session ที่เก็บวันนี้ยังไม่ฝาก) และ "สะสมทั้งหมดยังไม่ฝาก" (sum ของ session ทุกวันที่ยังไม่ฝาก รวมวันนี้ด้วย) — sticky บนสุดของหน้า
4. **AI (Gemini 2.5 Flash) อ่านสลิป** → prefill ยอด+ชื่อบัญชีปลายทาง ให้พนักงานเห็นแล้วกดยืนยันเอง ไม่ auto-submit — **บังคับตั้ง `thinkingConfig.thinkingBudget=0`** (บั๊กที่เคยพังเงียบมาแล้วจริงใน ChairOps ต้องไม่พังซ้ำ)
5. **Mismatch (ยอด/ชื่อบัญชีไม่ตรง/สลิปซ้ำ)** → ตั้ง `approvalStatus="PENDING"` (ค่าเดิมที่มีอยู่แล้ว ไม่เพิ่ม enum ใหม่) + เขียน `ocrFlagReason` อธิบายเหตุผล → ถูก `pushBranchDepositsToLedger` กันออกจาก ledger อัตโนมัติอยู่แล้ว (ไม่ต้องแก้โค้ดจุดนั้นเลย) → ไปโผล่ในหน้า review ที่ office มีอยู่แล้ว (`deposits-client.tsx`)
6. **ไม่บล็อกการฝากที่หน้าพนักงานเลย** ไม่ว่า mismatch แบบไหน — พนักงานฝากได้เสมอ, การอนุมัติเข้าบัญชีกลางต่างหากที่ถูก gate
7. **ฝากย้อนหลังได้ไม่จำกัดวัน** (CEO ตัดสิน) — ป้องกันด้วย **append-only**: ห้าม delete/edit หลักฐานที่แนบไปแล้ว, เพิ่มหลักฐานใหม่ได้ (ไม่ทับของเดิม) ตาม pattern "หลักฐานเปลี่ยนไม่ได้" ที่ระบบมีอยู่แล้ว (`attachEventPhotos`)
8. **Duplicate-slip check**: เทียบเลขอ้างอิงธนาคาร (ref number) org-wide ก่อนเสมอ, ถ้าอ่าน ref ไม่ได้ fallback ไปเทียบวันที่โอนจริง(จากสลิป)+ยอด scoped ตาม `bankAccountId` (ผ่าน `CfBranchReconcileConfig`)
9. **Silent-failure canary ตั้งแต่วันแรก**: เก็บ `ocrReadable` (true/false/null แยกจาก "อ่านได้แต่ field ว่างจริง") + เรียก Gemini จริงกับสลิปตัวอย่าง ≥8-10 ใบก่อน launch (ไม่ใช่แค่ build เขียว) + alert ถ้า field ที่ควรอ่านได้เป็น null ต่อเนื่องผิดปกติ
10. **Build เป็น 2 ก้อนในรอบเดียวกัน** (ไม่ทิ้งช่วงห่างข้ามสปรินท์): ก้อน 1 = ลิงก์+session picker+โชว์ยอด 2 ตัว (ของเดิม 90%, ความเสี่ยง deploy ต่ำสุดเพราะไม่แตะ schema) → ปล่อยก่อนได้ทันทีที่เสร็จ; ก้อน 2 = AI OCR+fraud-check (ของใหม่จริง มี schema migration) → ตามติดทันที ไม่ defer ข้ามสปรินท์ตามที่ CEO สั่ง

## 5. 🔗 Integration Map

**Reuse (ไม่แก้ logic เดิม):**
- `recordCashDeposit()` (`lib/clawfleet/deposit-actions.ts:94`) — เรียกตรงจาก UI ใหม่ ไม่แก้ signature หลัก มีแต่เพิ่ม field เสริม (ocr* ไม่บังคับ)
- `getPendingDeposits()` (`lib/clawfleet/deposit-queries.ts:88`) — ใช้เป็นข้อมูล session picker
- `PhotoCaptureButton` (`components/clawfleet/photo-capture-button.tsx`) — reuse ทั้งฟังก์ชัน (resize, offline queue, retry, cap 500KB)
- `pushBranchDepositsToLedger` (`lib/clawfleet/reconcile/ledger-push.ts`) — ไม่ต้องแก้เลย เพราะ exclude `PENDING` อยู่แล้ว
- Transaction/race-guard เดิม (`deposit-actions.ts:203-236`, atomic `updateMany WHERE depositId IS NULL` ใน `$transaction`) — พิสูจน์แล้วว่ากันการฝากซ้ำ session เดียวกันได้ ไม่ต้องเพิ่ม lock ใหม่
- Gemini call pattern จาก ChairOps (`lib/chairops/reconcile/slip-ocr.ts`) — **ดึงชั้น "เรียก Gemini + parse JSON" ออกมาเป็น lib กลาง** ที่ทั้ง 2 โปรแกรมเรียกร่วมได้ (ล็อก `thinkingBudget=0` ไว้ระดับ helper ไม่ใช่แค่ comment) ส่วนชั้น "เช็คซ้ำในตาราง" fork แยกเขียนใหม่ผูกกับ `CfCashDeposit` โดยเฉพาะ (ห้าม cross-import ข้ามโปรแกรมตรง ๆ — ผูก deploy lifecycle 2 โปรแกรมเข้าด้วยกัน)

**Schema ใหม่ (additive, nullable ทั้งหมด, ไม่แตะ field เดิม):**
- `CfCashDeposit` เพิ่ม: `ocrAmountCents Int?`, `ocrAccountName String?`, `ocrRefNo String?`, `ocrTransferDatetime DateTime?` (วันที่โอนจริงจากสลิป — informational, ไม่ใช่ hard-gate เพราะ CEO เลือก append-only แทน day-cap), `ocrReadable Boolean?` (แยก "อ่านไม่ออก" จาก "field ว่างจริง"), `ocrReadAt DateTime?`, `ocrFlagReason String?`
- ใหม่: append-only attachment ให้รองรับ "อัปโหลดสลิปเพิ่มได้ไม่จำกัด ห้ามลบของเดิม" — เพิ่มตารางลูก `CfCashDepositAttachment` (id, depositId FK, url, uploadedAt, uploadedById) แทนการเปลี่ยน `slipPhotoUrl` เดิม (คง `slipPhotoUrl` ไว้เป็นรูปแรก/หลัก เพื่อ backward-compat) — เขียนได้อย่างเดียว ไม่มี route ลบ/แก้
- `/api/clawfleet/upload` PHASES: เพิ่ม `"deposit_slip"` (pure code, ไม่ migration)

**ไม่แตะ:** `approvalStatus` enum เดิม (reuse `PENDING`), `Branch`/`CfBranchReconcileConfig` shared tables (อ่านอย่างเดียวเพื่อดึงชื่อบัญชีไปเทียบ), `/clawfleet/os/deposits` หน้าเดิม (ยังทำงานเหมือนเดิมทุกจุด)

**Role/Access:** ไม่ต้องแก้ authorization — `isCustodyHolder` gate เดิมครอบคลุมอยู่แล้ว, layout gate เช็คแค่ module+role (รวม staff) พอ

**Design tokens:** ใช้ pattern "กดสลับดูยอด" (tap-to-toggle) จาก ClawFleet matrix grid เดิมสำหรับ breakdown ยอดสะสม, สีธงแดงตัวหนังสือเข้ม (ไม่ใช่กรอบจาง) จาก ChairOps สำหรับข้อความเตือน — **ห้าม hover/title tooltip เด็ดขาด** (CEO เช็คมือถือเป็นหลัก)

## 6. 🧩 Feature Spec (MoSCoW)

### Must
- ปุ่ม/แถบ "ฝากเงิน" sticky บนสุดของหน้าประวัติเก็บ (~56px) โชว์ 2 ตัวเลขแยกกัน: "วันนี้ต้องฝาก ฿X" และ "สะสมยังไม่ฝาก ฿Y" (Y ≥ X เสมอ)
- กดฝากเงิน → เปิด inline panel ไม่เปลี่ยนหน้า → session picker (ติ๊กเลือกจากลิสต์ `getPendingDeposits()`) → ถ่าย/แนบสลิป (reuse `PhotoCaptureButton`) → AI อ่านยอด+ชื่อบัญชี prefill ให้เห็น → พนักงานกดยืนยัน → `recordCashDeposit()`
- แนบสลิปได้ทั้งวันเดียวกันและย้อนหลังไม่จำกัดวัน — เก็บเป็น append-only (ห้าม delete/edit หลักฐานเดิม)
- Mismatch (ยอด/ชื่อบัญชี/ซ้ำ) → `approvalStatus=PENDING` + `ocrFlagReason` → auto-excluded จาก ledger push (ของเดิมทำอยู่แล้ว) → โผล่ในหน้า review เดิมของ office
- Silent-failure canary + ทดสอบ Gemini จริงกับสลิปจริง ≥8-10 ใบก่อน launch

### Should
- เพิ่ม `ocrTransferDatetime` โชว์เทียบกับวันที่บันทึกในระบบ (informational banner ถ้าห่างกันมาก — ไม่บล็อก ไม่จำกัดวัน ตามที่ CEO สั่ง แค่ให้ office เห็นสัญญาณ)
- Perceptual/image hash ของไฟล์สลิปทุกใบ เทียบกับที่เคยอัปโหลดทั้งองค์กร — จับสลิปซ้ำได้แม้ OCR อ่านค่าตัวเลขไม่ออกเลย (ของเสริมที่ ChairOps ยังไม่มี ต้นทุนต่ำ ประโยชน์สูง)
- แถวประวัติการฝากที่สำเร็จ ไหลกลับเข้า list หลักเป็น `kind='deposit'` กดดูรูปสลิป+ผล AI ย้อนหลังได้ (reuse `photos[]` mechanism เดิม)

### Could
- แจ้งเตือนผู้จัดการอัตโนมัติถ้ายอดสะสมค้างเกิน N วันแบบผิดปกติ (แค่แจ้งเตือน ไม่บล็อก — เข้ากับ CEO's no-cap decision)
- รวม OCR helper เป็น shared lib ที่ ChairOps เองก็ปรับมาใช้ (ลด maintenance 2 ชุด) — ทำทีหลังเมื่อทั้ง 2 เสถียรแล้ว

### Won't (รอบนี้)
- ไม่ตั้งเพดานวันฝากย้อนหลัง (CEO ตัดสินใจแล้ว)
- ไม่บล็อกการฝากเงินที่หน้าพนักงานไม่ว่ากรณีใด
- ไม่แก้/ลบ `/clawfleet/os/deposits` หน้าเดิม

### Edge cases ที่ต้องเทส (จาก QA/QC + Senior Programmer)
1. Gemini auth/thinkingBudget พังเงียบ (ทดสอบเรียกจริงก่อน launch เสมอ)
2. สลิปเก่าไม่มี ref number + ภาพเบลอ + backdate ข้ามหลายวัน → ต้อง route เข้า manual review เสมอ ห้าม auto-clear
3. 2 คนกดฝากพร้อมกันคนละ session (ปลอดภัยแล้วจาก transaction เดิม — regression test ยืนยันซ้ำ)
4. อัปโหลดไฟล์ 0 byte/corrupt → validate ก่อนบันทึกเสมอ
5. แนบสลิปผิดสาขา → derive สาขาจาก session ที่กำลังฝากอัตโนมัติ ไม่ให้พนักงานเลือกเอง (ตัดปัญหาที่ต้นทาง)
6. ชื่อบัญชีภาษาไทยยาว ตัดคำบนจอแคบ → ต้อง wrap ให้อ่านชื่อเต็มได้ก่อนตัดสินใจ
7. เน็ตหลุดระหว่างอัปโหลด → ต้องเห็นสถานะ "รอวิเคราะห์"/"สำเร็จ"/"ไม่สำเร็จ" ชัดเจน ไม่เงียบ (reuse offline-queue เดิมของ `PhotoCaptureButton`)
8. สาขาที่ยังไม่ผูก `CfBranchReconcileConfig.bankAccountId` → ข้ามการเช็คชื่อบัญชีแบบไม่บล็อก แต่ต้องมีสัญญาณให้เห็นว่า "ยังเช็คบัญชีไม่ได้" ไม่ใช่เงียบเหมือนเช็คผ่าน

## 8. ⚠️ Risks (Top 5) + 🚫 Out of Scope

**Risks:**
1. ไม่มีเพดานวันฝากย้อนหลัง (CEO ตัดสินใจแล้ว) — ยังมีความเสี่ยงที่พนักงานถือเงินไว้นานผิดปกติก่อนฝาก ลดความเสี่ยงบางส่วนด้วย "สะสมยังไม่ฝาก" ที่โชว์เด่นชัดบนหน้า (เห็นทันทีถ้ายอดพอกพูน) + แจ้งเตือน office ถ้าค้างผิดปกติ (Should item)
2. Gemini OCR พังเงียบซ้ำ (เคยเกิดมาแล้ว 2 รอบใน ChairOps) — ป้องกันด้วย canary + ทดสอบสลิปจริงก่อน launch
3. Migration บน `CfCashDeposit` ที่ใช้งานจริงอยู่แล้ว — ทุกคอลัมน์ nullable, ไม่แตะ field เดิม, apply migration ก่อน deploy โค้ดเสมอ
4. Perceptual hash (Should item) เพิ่ม complexity เล็กน้อย — ชั่งกับประโยชน์การจับโกงที่ OCR อ่านไม่ออก
5. Cross-branch duplicate check (org-wide ref number) อาจมี false positive ถ้าสองสาขาบังเอิญมีธุรกรรมยอด+วันที่ตรงกันแต่คนละธนาคาร — บรรเทาด้วยการใช้ ref number (unique จริง) เป็นหลักก่อนเสมอ

**Out of scope รอบนี้:** เพดานวันย้อนหลัง, การบล็อกการฝากเงิน, การแก้หน้า `/clawfleet/os/deposits` เดิม, shared OCR lib ข้ามโปรแกรม (ทำทีหลัง)
