## 1 · Executive Summary
- ChairOps มีปัญหาเชิงโครงสร้าง 2 ก้อนใหญ่ที่กระทบ 'ตัวเลขเงินขาด' ซึ่งเป็นหัวใจของระบบ: (1) เครื่องคำนวณเงินขาดยังตั้งค่า default เป็นโหมด 'สะสมทั้งชีวิตสาขา' (legacy) — ยืนยันแล้วในโค้ด resolveMode() ที่ล।่าวเป็น legacy เว้นแต่ตั้ง env=window — ซึ่งขัดกฎ CEO ที่สั่งห้ามสะสมเงินขาด และยังไม่มีปุ่ม 'ปิดงวด' (FIN-01, CO-WF-05).
- (2) ตัวเลขเงินขาดวัดผิดฐาน: ระบบเอา 'ยอดที่ฝากเข้าแบงค์' มาเทียบ ไม่ใช่ 'ยอดที่แม่บ้านนับได้' — เงินที่นับได้แต่ฝากไม่ครบจะหายไปจากการตรวจ และไม่มีการกระทบยอดกับ statement ธนาคารจริงเลย (deposit ไม่เคยถูก match กับเงินเข้าจริง) ทำให้ 'ยืนยันเงินเข้า' เป็นแค่คำพูดบนกระดาษ (FIN-02, FIN-03, FIN-07).
- ความเสี่ยงข้อมูลรั่วข้ามบริษัทมีจริงและพิสูจน์แล้ว 4 จุด: หน้าดูพนักงานไม่กรองบริษัท (ADMIN เห็นพนักงานบริษัทอื่น), ปุ่มสั่งคำนวณเงินขาดข้ามบริษัทได้, และ cron แจ้งเตือนหลายตัว query ข้ามทุกบริษัทแล้วยิงเข้า LINE กลุ่มเดียว — ถ้าขาย ChairOps ให้ลูกค้ารายที่ 2 ชื่อสาขาจะรั่วทันที (SEC-02, CO-QA-02, CO-QA-03, CO-BE-04).
- ตัวเลขที่ CEO เห็นบนจอ 'พึ่งไม่ได้' เพราะงานคำนวณหลังบ้านถูก Vercel ตัดกลางทาง: ตอน commit ข้อมูล POS ระบบยิงคำนวณเงินขาดแบบ 'ส่งแล้วไม่รอผล' (void Promise) — ยืนยันที่ actions.ts:1104 — พอ response เด้งกลับ runtime ก็ freeze เลขขาด/เตือนเลยไม่อัปเดต และ cron สำรองก็รันแค่วันละครั้ง (CO-BE-01, CO-BE-02).
- ช่องโหว่ข้อมูลเข้า: อัปโหลด CSV ไม่เขียนตารางรายได้รายวันที่ตัวคำนวณโหมดใหม่ใช้อ่าน (ยืนยันคอมเมนต์ 'CSV path = skipped') → เงินขาดโชว์ปลอมเป็น 0 และระบบเตือน 'POS ขาด' ตลอด; รวมถึง coin/เหรียญในไฟล์อาจถูกตีความเป็นเงินผิด (CO-QA-01, CO-QA-05).
- ฝั่งหน้าจอ/การใช้งาน: 4 หน้าที่ทำงานจริง (รวมคิวตรวจสอบ maker-checker) หาไม่เจอบนเมนูเดสก์ท็อป, มีเมนูตายซ่อนอยู่ 1 ชุด, นาฬิกานับถอยหลัง cut-off เพี้ยน 7 ชม. และการ์ด 'แม่บ้านยังไม่ส่ง' ขึ้นแดงตั้งแต่เช้าทั้งที่ยังไม่ถึงเวลา — สร้าง false alarm รายวัน (IA-01, IA-02, CO-WF-01, CO-WF-02).

## 2 · Root-Cause Clusters (fix these, not 23 symptoms)

### 1. [P0] เครื่องคำนวณ 'เงินขาด' วัดผิดฐาน + สะสมตลอดกาล — เลขที่ CEO เห็นไม่ใช่ความจริงทางบัญชี
- **สมาชิก:** FIN-01, FIN-02, FIN-03, FIN-04, FIN-06, FIN-07, CO-QA-04, CO-QA-06, CO-WF-05
- **ทำไมสำคัญ:** นี่คือหัวใจของ ChairOps ทั้งระบบ — ตัวเลข 'เงินขาด' ที่ใช้จับคนโกง/คนสะเพร่า. ยืนยันในโค้ดแล้วว่า: (1) โหมด default = legacy บวกสะสมทั้งชีวิตสาขา (resolveMode() drift-engine.ts:71) ขัดกฎ CEO 'ห้ามสะสมเงินขาด' และยังไม่มีปุ่มปิดงวด (lastReconcileClosedAt ไม่เคยถูกเซ็ต); (2) วัดด้วย 'ยอดฝากแบงค์' (depositedAmount+bankFee+writeoff) ไม่ใช่ 'ยอดแม่บ้านนับได้' (countedAmount) — เงินที่นับได้แต่ฝากไม่ครบ 'หายเนียน' จากการตรวจ; (3) ยอดที่ติดธงรอตรวจ (≥500฿) ถูกนับลดเงินขาดทันทีก่อนออฟฟิศยืนยัน = เคลียร์ยอดขาดปลอม; (4) write-off และ POS ใช้คนละแกนเวลา ทำให้ตัดหนี้สูญไปลดยอดผิดงวด. ผลรวม: เลขขาดทั้งเชื่อถือไม่ได้ และผู้สอบบัญชีกระทบยอดไม่ได้.
- **ทิศทางแก้:** ทำเป็นงวด ไม่ใช่ตลอดกาล: สร้าง action 'ปิดงวด' (เซ็ต lastReconcileClosedAt) แล้ว flip CHAIROPS_DRIFT_MODE=window ใน Vercel — แต่ต้องยืนยัน CEO ก่อน flip เพราะค่าจะกระโดด (ยอดสะสมเก่าจะหาย). แยกการกระทบยอดเป็น 3 ชั้นที่ผู้สอบบัญชีต้องการ: POS cash↔Σ countedAmount (แม่บ้านเก็บครบไหม), Σ counted↔Σ deposited (ฝากครบไหม), deposit↔bank statement จริง (เงินเข้าจริงไหม — ปัจจุบันไม่มีเลย ต้องเพิ่ม bank-recon แบบ LedgerLine). เก็บ collectedShortfall/depositShortfall แยกคอลัมน์. ยอดรอตรวจ (requiresReview) แสดงเป็น pending แยก ไม่นับลดจนออฟฟิศ clear. ผูก write-off กับงวดที่หนี้เกิด ไม่ใช่วันอนุมัติ. ทุกแก้ตัวเลข = ต้องผ่าน FIN+OFC+AUD lens.

### 2. [P0] ข้อมูล POS เข้าระบบแบบ all-or-nothing + งานคำนวณถูก Vercel ตัดกลางทาง → ตัวเลขบนจอ stale/ปลอม
- **สมาชิก:** CO-QA-01, CO-BE-01, CO-BE-02, CO-BE-03, CO-WF-03, CO-WF-04
- **ทำไมสำคัญ:** ต่อให้สูตรคำนวณถูก แต่ถ้าข้อมูลเข้าไม่ครบหรือคำนวณไม่จบ เลขก็ผิด. ยืนยันแล้ว: (1) path อัปโหลด CSV ข้ามการเขียน ChairopsBranchDailyRevenue (คอมเมนต์โค้ด 'CSV path = skipped' actions.ts:~998) — ตารางนี้คือที่ drift โหมด window + watchdog อ่าน → ผลคือเงินขาดโชว์ 0 ปลอม และเตือน 'POS ขาด' ตลอดสำหรับร้านที่ใช้ CSV; (2) ตอน commit ยิงคำนวณเงินขาด+เตือนแบบ fire-and-forget (void Promise.allSettled actions.ts:1104) — Vercel freeze หลัง response เด้ง งานเลยไม่จบ เลขไม่อัปเดต; (3) cron สำรองรันแค่วันละครั้งทั้งที่โค้ดเชื่อว่ารันทุก 30 นาที = backstop ช้า 24 ชม.; (4) ไฟเขียวสถานะ cron ที่ footer hardcode เขียวตลอด — cron ตายก็ยังเขียว, CEO ไม่มีทางรู้.
- **ทิศทางแก้:** Source of truth เดียวสำหรับ 'POS เงินสด/วัน': ทำให้ทั้ง path CSV และ XLSX เขียน ChairopsBranchDailyRevenue เหมือนกัน (หรือให้ drift+watchdog UNION 2 ตารางเสมอ ไม่ fallback all-or-nothing). เปลี่ยนงานคำนวณ critical เป็น await: ใช้ next/server after() ห่อ background work ให้ runtime รอจนจบก่อน freeze — อย่างน้อย drift ของสาขาใน batch ต้อง await sync (commit นี้ optimize เหลือ ~3 query/branch แล้ว พอ await ได้); alert/autoResolve ใช้ after(). ใส่ skipDuplicates:true บน createMany ทุกจุดกัน P2002 rollback. ตัดสินใจ cron: ถ้าต้องการเตือนใกล้ real-time แก้ vercel.json เป็น */30 (โปรเจกต์ใช้ Pro), ถ้ายอมวันละครั้งให้ลบคอมเมนต์ลวง. แทนไฟเขียว hardcode ด้วยการอ่าน cron_runs จริง.

### 3. [P1] กำแพงแบ่งบริษัทเป็นของประดับ — IDOR + ข้อมูลรั่วข้าม tenant (ระเบิดเวลาตอนขายลูกค้ารายที่ 2)
- **สมาชิก:** SEC-01, SEC-02, CO-QA-02, CO-QA-03, CO-BE-04, CO-WF-07
- **ทำไมสำคัญ:** ChairOps พึ่ง orgId ใน app-level ล้วน — ยืนยันแล้วว่า prisma.ts ใช้ PrismaClient ธรรมดา connection เดียว ไม่มี RLS-subject role/ไม่มี org auto-scope (มี TODO แต่ไม่ทำ) → RLS ที่เขียนใน migration ไม่ทำงานบนเส้นทาง Prisma เลย. แปลว่าทุก query ที่ลืม where orgId = ประตูเปิด. พิสูจน์แล้ว 4 จุด: users/[id]:77 ดึง user ไม่กรอง orgId (ADMIN เห็น PII พนักงานบริษัทอื่น), recomputeDriftForBranchAction สั่งคำนวณ+เขียน drift สาขาบริษัทอื่นได้ (IDOR เขียน), และ cron eod-reminder/sop-check/ceo-digest query chairopsBranch ข้ามทุก org แล้วยิงเข้า LINE กลุ่มเดียว (global env). ตอนนี้มี 1 tenant เลยยังไม่ระเบิด — วินาทีที่ขาย SME รายที่ 2 ชื่อสาขา/ยอดเงิน/พนักงานรั่วทันที. กระทบ PDPA ด้วย.
- **ทิศทางแก้:** ระยะสั้น (ก่อนขาย tenant ที่ 2 = บังคับ): ปะ IDOR ทุกจุดด้วย findFirst({where:{id, orgId: session.user.orgId}}) + notFound/error; เพิ่ม orgId เข้าทุก cron loop แบบ per-org (for org of orgsWithChairops { where:{orgId} ... notify(org) }) และผูก LINE group id ต่อ org เก็บใน DB แทน env เดี่ยว; ใส่ guard ปฏิเสธ global broadcast ถ้ามี >1 org. ระยะยาว (กระทบสถาปัตยกรรม — เสนอ CEO เลือก): ทำ Prisma extension auto-inject orgId scope (ตาม TODO ในโค้ด) หรือสลับ user-request ไปใช้ DB role ที่ subject-to-RLS + set request.jwt.claim.sub ต่อ request. อย่างน้อยเพิ่ม lint/test ที่ fail ถ้า chairops query ไม่มี orgId ใน where เพื่อกันลืมรอบหน้า.

### 4. [P1] Race condition / idempotency ในการฝากเงิน + คำนวณ — เสี่ยงฝากซ้ำ/นับซ้ำที่ระดับ DB
- **สมาชิก:** FIN-05, CO-BE-06, CO-BE-07, CO-QA-09
- **ทำไมสำคัญ:** เป็นเงินจริง — กดปุ่มฝาก 2 ครั้งพร้อมกันต้องไม่ฝากซ้ำ. batchDeposit query collections โดยไม่กรอง depositId:null และพึ่ง check ใน JS แทน DB guard (actions.ts:422-440) → ถ้า 2 request วิ่งพร้อมกันมีช่อง race ที่ collection เดียวถูกผูก 2 deposit. createCashCollection: drift recompute หลัง transaction ไม่ await ครอบใน try → ถ้า recompute throw จะหลุดเป็น unhandled แต่ collection commit ไปแล้ว = เลข stale เงียบ ๆ. และ recomputeAllDrifts CONCURRENCY=5 ถูกเรียกซ้อนจาก gmail-import หลาย org พร้อมกัน → fan-out ระเบิดเกิน pooler ตอนหลาย tenant.
- **ทิศทางแก้:** ย้าย guard ลง DB layer: ใส่ depositId:null ทั้งใน findMany และ updateMany WHERE แล้วเช็ค res.count===collectionIds.length ภายใน $transaction ถ้าไม่ครบให้ throw rollback → idempotent กันฝากซ้ำที่ระดับ DB จริง (ตาม RULE I). batchDeposit OFFICE-tier ต้อง verify branchOverride เป็นของ org ก่อน. ครอบ drift recompute หลัง transaction ด้วย try/catch + after(). คุม fan-out recomputeAllDrifts เมื่อหลาย org (queue/lock ต่อ org กัน pooler ระเบิด).
