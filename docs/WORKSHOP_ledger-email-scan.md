## 1. 🎯 Goal & Success Metrics
**A) Email-scan:** ต่อ Gmail การเงิน → สแกนหาเมลใบเสร็จ → AI อ่าน → สร้าง "ใบร่าง" รอบัญชีตรวจ (แบบ Paypers แต่รวม LINE+อีเมลที่เดียว).
**B) Combine-button:** รวบ "เพิ่มค่าใช้จ่ายไม่มีใบเสร็จ" + "ออกใบรับรองแทนใบเสร็จ (SUB)" เป็นทางเข้าเดียว.

**Success metric:** % ค่าใช้จ่ายที่เข้าระบบอัตโนมัติจากเมล (ไม่ต้องพิมพ์เอง) · junk-rate (ใบร่างที่ถูกทิ้งไม่ยืนยัน ÷ ใบร่างที่สร้าง) ต่ำ · เวลาที่บัญชีใช้เคลียร์ inbox/วัน ลดลง.
**Definition of Done:** กดสแกนเอง → เห็นใบร่างจากเมลในแท็บ "อีเมล" ของหน้าตรวจเดิม · ทุกใบเป็น draft · companyId ถูกต้อง · ไม่ซ้ำกับ LINE · ปุ่มเดียว B ออกใบแทนได้จบในไหลเดียว (ผ่าน gate เดิม).

## 3. 🗣️ Debate Highlights (ทีมเถียงกัน → ตัวอ่านโค้ดจริงตัดสิน)
- **"sha256 dedup ต้องสร้าง migration ใหม่ไหม?"** — SA/Architect/Devil บอกหา `@@unique` ใน Prisma ไม่เจอ = ต้องทำใหม่. **ตัวอ่านโค้ดค้าน:** partial-unique index `ledger_expense_org_company_sha256_key` มีอยู่จริงใน prod (raw DDL migration `20260603120000`) → กันซ้ำข้ามช่อง LINE+อีเมลได้ฟรี **0 migration**.
- **"PDF ต้องแก้ AI parser + ลง sharp ไหม?"** — Programmer/QC บอกต้องแก้. **ตัวอ่านโค้ดค้าน:** `ai-parse.ts` รับ MIME `application/pdf` อยู่แล้ว — แค่ส่ง data-URL ให้ถูก = **ไม่ต้องแก้ parser, ไม่ต้องลง sharp**. เหลือแค่เทสต์ว่า Gemini อ่าน PDF ใบกำกับไทยแม่นพอไหม (~1 ชม.).
- **"ปุ่มเดียว B ออกใบแทนบนใบร่างเลยได้ไหม?"** — UX/End-user อยากให้ลื่นปุ่มเดียวจริง. **นักบัญชี/ตัวอ่านโค้ดค้าน:** route ใบแทนบังคับ `status=confirmed` (เป็น "เส้นแบ่งความปลอดภัย ห้ามโพสต์อัตโนมัติ") → ปุ่มเดียว = **1 ทางเข้า** (สร้างร่าง+เหตุผล → บัญชียืนยัน → พิมพ์ใบแทน) ไม่ใช่ปลด gate.
- **"buyer-match reuse ได้เลยไหม?"** — BA/UX/Owner บอก plug-and-play. **นักบัญชีค้าน (ยืนยันโดยโค้ด):** `group-identity.ts` ฮาร์ดโค้ด JP Sync บริษัทเดียว (`0305564001581`) + มี TODO รอ whitelist เครือ → ใบของ **Pooil** ที่มาจากเมลจะถูกตัดสิทธิ์ขอคืน VAT. ต้องทำ buyer-match แบบรู้บริษัท **ก่อน** เปิดเมล.
- **"cron slot ไหน?"** — `0 2` ที่เสนอ **ชนกับ** access-review เดิม → ใช้ช่องว่าง `0 3 * * *`. (Vercel จำกัด 1 ครั้ง/วัน/path ไม่ใช่ 1 cron ทั้งระบบ).
- **"window.prompt เก็บเหตุผลใบแทน"** — พังเงียบใน LINE/LIFF webview → ต้องเปลี่ยนเป็นฟอร์มในหน้า.

## 4. ✅ Consensus Decisions (ทีมตกลงร่วม)
1. **ส่ง B (ปุ่มเดียว) ก่อน** เป็น workstream แยก — เสี่ยงต่ำ reuse สูง ~0.5 วัน. gate เดิมไม่แตะ.
2. **A reuse ~80%** — Gmail client + cron skeleton + AI parser + draft path + sha256 + enum "email" มีหมด. ของใหม่ = findReceiptAttachments, ตาราง LedgerEmailConnection, ตาราง ledger_email_message, buyer-match รู้บริษัท, cron route, source filter, LIFF list.
3. **Draft เท่านั้นตลอดกาล** — เมลไม่ auto-confirm/ไม่ auto-post TRCloud/ไม่ auto-claim VAT. คนยืนยันทุกใบ.
4. **กันซ้ำ 2 ชั้น** — (1) `ledger_email_message.gmailMessageId` กันก่อนเรียก AI (ประหยัดเงิน+idempotent) (2) sha256 index เดิมกันข้ามช่อง. AI ไม่ใช่ key กันซ้ำ.
5. **ตัวกรองบังคับก่อน cron** — v1 = sender-allow-list + Gmail label. ไม่มีตัวกรอง = cron ไม่รัน.
6. **companyId แก้ได้หรือพักไว้ต่อใบ** — fail-closed เป็น "ต้องระบุบริษัท" ห้าม default org-wide.
7. **PDF v1 พักเป็น needs-manual** (เก็บไฟล์ไว้ ไม่สร้างใบขยะ) จนกว่าเทสต์ผ่าน · รูป parse ได้วันแรก · ไม่ลง npm ใหม่โดยไม่ขอ CEO.
8. **กดสแกนเอง dogfood 1-2 สัปดาห์ ก่อนเปิด cron อัตโนมัติ** · สแกนแรกย้อน 30 วัน แล้ว incremental.
9. **2 ตารางใหม่เท่านั้น:** `ledger_email_message` (กันซ้ำ+audit+suppress-list+run-summary+idempotent) + `LedgerEmailConnection` (company-scoped + filters + suppressedSenders).
10. **Suppress-list** — กด "ไม่ใช่ค่าใช้จ่าย/ทิ้ง" → เขียน sender ลง suppressedSenders → สแกนรอบหน้าตัดออก (คิวล้างตัวเอง).
11. **ใบร่างเมลลงหน้าตรวจเดิม (ExpenseReviewPane) ผ่านแท็บ "อีเมล"** — ไม่มีหน้า inbox ใหม่ · ต้องเห็นบน LIFF/มือถือด้วย (กางใหม่).
12. **Flag-gated `LEDGER_EMAIL_SCAN_V1`** · flag-off = byte เท่าเดิม · แยกขาดจาก ChairOps autoIngest (OCR พังห้ามทำ StarThing พัง).

## 5. 🔗 Integration Map — เชื่อมของเดิมยังไง (REUSE vs BUILD-NEW)
**REUSE (ไม่สร้างใหม่):**
- Gmail REST client `lib/chairops/email/gmail.ts` (search/getMessage/downloadAttachment/getAccessToken/encrypt-decrypt/exchangeCode) — ยกมาทั้งก้อน (แนะนำลิฟต์เป็น `lib/google/gmail.ts` + re-export shim กัน crypto drift).
- AI parser `lib/ledger/ai-parse.ts` `parseReceipt` AS-IS (รับ PDF อยู่แล้ว, budget-guarded).
- Draft write `createDraftExpenseSystem` (cron, ไม่มี session, companyId บังคับ, draft บังคับ) / `createDraftExpense` (ปุ่ม B). source='email' รับอยู่แล้ว — 0 migration.
- Dedup `sha256Hex` + index `ledger_expense_org_company_sha256_key` (DB-race-safe, 0 migration).
- SUB voucher route + `lib/ledger/vouchers.ts` **ไม่แตะ** — ปุ่ม B แค่ orchestrate create→confirm→SUB ผ่าน gate เดิม.
- source-filter: เพิ่ม param `source` ใน `ExpenseListFilter`/buildWhere (code-only, 0 migration).

**BUILD-NEW:**
- `findReceiptAttachments` (image/* + application/pdf) — clone จาก findXlsxAttachments (~15 บรรทัด).
- ตาราง `ledger_email_message` (orgId, companyId, gmailMessageId UNIQUE, status, sender, subject, receivedAt, scanRunId, ocrConfidence, expenseId?) — เขียน **ก่อน** เรียก AI. (migration หลัก)
- ตาราง `LedgerEmailConnection` (per orgId+companyId: refreshTokenEnc, scopes, gmailEmail, lastSync*, filterSenders[], suppressedSenders[], firstScanDone). **ไม่ reuse** ChairopsGmailConnection (orgId-only, ผูกบริษัทไม่ได้ + คับ OAuth ข้ามโมดูล).
- buyer-match รู้บริษัท: generalize `group-identity.ts` → `gradeBuyerMatch(buyerTaxIdOnDoc, targetCompany.taxId)` (เป็นทั้งตัว route companyId + เกรด VAT). **PREREQUISITE ของ A**.
- cron route `/api/ledger/cron/email-scan` (clone chairops/cron/gmail-import + requireCronSecret + runWithMonitor + maxDuration) + vercel.json ช่อง `0 3 * * *`. วนเฉพาะ LedgerEmailConnection ไม่ใช่ทุก org.
- ปุ่ม B: modal เดียว (ฟิลด์ไม่มีใบเสร็จ + ฟอร์มเหตุผล inline แทน window.prompt) บน primitive เดิม — ไม่มี route ใหม่ ไม่ปลด gate · ต้องขึ้น LIFF/มือถือ.
- LIFF email-draft list "รายการรอตรวจ" — `app/liff/ledger` ปัจจุบัน capture-only ไม่มี list.

**Memory guardrails ที่ต้องเคารพ:** companyId ทุก query ([[feedback-ledger-query-must-filter-companyid-2026-06-06]]) · golden-rule never-auto-post · TRCloud = book-of-record (complement) · gmail.readonly = restricted scope (unverified-app/CASA) · ledger Gmail consent ต้อง `include_granted_scopes=true` กันหด Drive scope.

## 6. 🧩 Feature Spec (MoSCoW)
**MUST:** B ปุ่มเดียว (ผ่าน gate เดิม, ฟอร์มเหตุผล inline) · A: draft-only · companyId-or-park · buyer-match รู้บริษัท · dedup 2 ชั้น · filters บังคับ · LedgerEmailConnection ใหม่ · consent include_granted_scopes · findReceiptAttachments (PDF park) · แท็บ source=email ในหน้าตรวจเดิม · flag-gated แยกจาก ChairOps · cron `0 3` + requireCronSecret.
**SHOULD:** สแกนเองก่อน cron 1-2 สัปดาห์ · 30-day backfill + preview-before-import · suppress-list · run-summary ไทย + การ์ดสุขภาพการเชื่อม RED · 🟢🟡🔴 + badge "VAT ยังคืนไม่ได้" บนใบเมล · LIFF list view · provenance ครบต่อใบ (RD audit) · ลิฟต์ Gmail client เป็น shared lib.
**COULD:** junk-rate KPI · sender→company mapping zero-touch · lookback ปรับได้ (7/30/90) · body-HTML parsing · subject-keyword filter (v1.1) · verified inline-PDF path.
**WON'T (v1):** ปลด gate SUB · auto-confirm/auto-post ใบมั่นใจสูง · default companyId เป็นบริษัทแรก · AI เป็น key กันซ้ำ · ลง sharp โดยไม่ขอ · หน้า inbox แยก · subject-keyword v1 · ซื้อ SaaS OCR/email · เปิด cron ก่อน dogfood · reuse ChairopsGmailConnection as-is.

**Edge cases (top):** เมลเดียวกันมาทั้ง LINE+อีเมล (sha256) · refresh token ตาย (การ์ด RED, ห้าม masquerade เป็น "วันนี้ไม่มีใบ") · PDF อ่านไม่ออก (park ไม่ทิ้ง) · ใบ Pooil buyer-match พลาด (ต้อง company-aware) · queue ท่วม 50 ใบ (preview gate) · sender สแปม (suppress-list) · maxDuration 30-day backfill (batch/paginate) · cron slot ชน (ใช้ 0 3).

## 8. ⚠️ Risks (Top 5)
1. **Cross-company VAT leak** ถ้า companyId ไม่ถูก → fail-closed needs-company.
2. **Google unverified-app/PDPA** อ่าน inbox การเงิน → ต้อง CEO ยอมรับ + เขียนกฎ retention.
3. **Token blowout** ถ้าไม่มี filter → filters บังคับ + per-message guard ก่อน AI.
4. **PDF อ่านไม่แม่น** → park เป็น manual จนเทสต์ผ่าน.
5. **OAuth scope หด** Drive ถ้า consent ไม่ใส่ include_granted_scopes.
