0 สรุปสำหรับผู้บริหาร (อ่าน 30 วินาที)

บริษัทกำลังสร้าง โปรแกรมภายในสำหรับฝ่ายขายน้ำมัน ที่ต้องแสดง ตำแหน่งรถบรรทุกแบบ real-time บนแผนที่ พร้อมสถานะการจัดส่ง

เราทราบว่าผู้ให้บริการมีข้อมูลนี้อยู่แล้ว (ส่งเข้ากรมการขนส่งทางบกตามกฎหมายทุกวัน) และแจ้งว่ามีให้เราเชื่อมได้ทั้ง 2 รูปแบบ เอกสารนี้รวบรวม:

  • คำถามที่เราขอคำตอบจากผู้ให้บริการ (ส่วน 2–3)
  • สิ่งที่อยากให้ผู้ให้บริการเตรียม/ส่งมอบ (ส่วน 4)
  • สิ่งที่ฝั่งเราจะเตรียมเอง (ส่วน 5)
  • รายการข้อมูล (data fields) ที่ต้องการ (ส่วน 6)

1 รูปแบบการเชื่อมต่อ + แบบที่เราเลือก

แบบ A · Pull (เราดึงเอา) ⭐ เลือกแบบนี้แบบ B · Push (ผู้ให้บริการยิงมา)
ทิศทางข้อมูลโปรแกรมเรา → เรียก API ผู้ให้บริการเป็นรอบ ๆ → ได้ตำแหน่งรถกลับมากล่อง GPS → server ผู้ให้บริการ → ยิงเข้าระบบเรา (เหมือนที่ส่งกรมขนส่ง)
ใครสร้างปลายทางผู้ให้บริการมี API อยู่แล้ว เราแค่เรียกเราต้องสร้างจุดรับ + ออกรหัสให้ผู้ให้บริการ
ความปลอดภัยสูง (เราเป็นฝ่ายเรียก ไม่เปิดช่องสาธารณะ)ต้องป้องกันจุดรับ + จำกัด IP
เหมาะกับงานเรา✅ "รถอยู่ไหนตอนนี้ + ส่งถึงรึยัง"เก็บเส้นทางละเอียดทั้งวัน (ทำทีหลังได้)
การตัดสินใจของเรา: ใช้ แบบ A (Pull) เป็นหลัก
👉 คำถามแรกสุดที่อยากให้ยืนยัน: บริษัทรองรับให้เราดึงข้อมูล (Pull API) ได้ใช่หรือไม่? ถ้าใช่ ขอดำเนินการตามส่วนที่ 2

2 คำถามหลัก — แบบ A (Pull API)

ขอให้ผู้ให้บริการตอบ

2.1 ปลายทาง (Endpoint) และวิธีเรียก

  1. Base URL / Endpoint ของ API ดู "ตำแหน่ง + สถานะรถ real-time" คืออะไร?
  2. เป็น REST API (HTTP + JSON) ใช่ไหม? ถ้าไม่ใช่ ใช้รูปแบบอะไร (SOAP / WebSocket / อื่น ๆ)?
  3. ขอ เอกสาร API ฉบับเต็ม + ตัวอย่าง Request/Response จริง (sample JSON)
  4. เรียกครั้งเดียวได้ ตำแหน่งรถทุกคัน เลยไหม หรือต้องเรียกทีละคัน?

2.2 การยืนยันตัวตน (Authentication)

  1. ใช้กุญแจแบบไหน — API Key / Token / OAuth / Username-Password?
  2. ขอ บัญชีทดสอบ + API Key สำหรับทดสอบ (sandbox) เพื่อต่อระบบลองก่อนใช้จริง
  3. กุญแจมี วันหมดอายุ ไหม? ต้องต่ออายุอย่างไร?

2.3 ข้อจำกัดการเรียก

  1. เรียกดูได้ บ่อยแค่ไหน? (เราอยากได้ ~ทุก 15–30 วินาที)
  2. มี จำกัดจำนวนครั้งต่อนาที (rate limit) ไหม? เท่าไหร่?
  3. ต้อง แจ้ง IP ล่วงหน้า (whitelist) ไหม? (ถ้าใช่ เราจะแจ้ง IP ให้)

2.4 ข้อมูลที่ได้กลับมา

  1. Response มี field อะไรบ้าง? เราต้องการอย่างน้อยตามส่วนที่ 6
  2. เวลา (timestamp) เป็น UTC หรือเวลาไทย? มี field "เวลาอัปเดตล่าสุด" ไหม?
  3. ถ้ารถ จอด/ดับเครื่อง/สัญญาณขาด ข้อมูลแสดงอย่างไร?

2.5 ข้อมูลย้อนหลัง (ถ้ามี)

  1. มี API ดูเส้นทางย้อนหลัง ไหม? ขอ endpoint + เอกสาร (ไว้ทำรายงาน/ยืนยันการส่ง)

3 คำถามสำรอง — แบบ B (Push) เผื่อใช้ภายหลัง

  1. ผู้ให้บริการยิงข้อมูลมาในรูปแบบ มาตรฐานกรมขนส่ง (DLT JSON) ตรง ๆ ใช่ไหม?
  2. ยิงมา ทุกกี่นาที และ กี่คันต่อครั้ง?
  3. ฝั่งผู้ให้บริการต้องการอะไรจากเรา — URL ปลายทาง, Username/Password, IP?
  4. ถ้า server เราล่มชั่วคราว มีระบบ ส่งซ้ำ/ส่งย้อนหลัง ไหม?

4 สิ่งที่อยากให้ผู้ให้บริการเตรียม

ผู้ให้บริการเตรียม/ส่งมอบ
  • เอกสาร API ของ Pull API + คำอธิบาย field ทุกตัว
  • ตัวอย่างข้อมูลจริง (sample Request/Response JSON) อย่างน้อย 1 ชุด
  • บัญชีทดสอบ + API Key/Token สำหรับทดสอบ (sandbox)
  • Base URL ของระบบทดสอบ และระบบจริง (production)
  • รายการรถทั้งหมดของเรา — ตาราง: เลขทะเบียน ↔ เลขกล่อง GPS (unit_id) ↔ รุ่นกล่อง (ดูเหตุผล 5.2)
  • ข้อจำกัดการใช้งาน — ความถี่, rate limit, ต้อง whitelist IP ไหม
  • ค่าใช้จ่าย (ถ้ามี) สำหรับการใช้ API
  • ช่องทางติดต่อทีมเทคนิค (อีเมล/เบอร์/LINE) กรณีติดปัญหา

5 สิ่งที่ฝั่งเราต้องเตรียม

ทีมพัฒนาฝั่ง Pooil

5.1 ระบบ

  • ตัวเรียก API (API client) ดึงตำแหน่งรถ
  • งานเบื้องหลังดึงข้อมูลเป็นรอบ ทุก ~15–30 วินาที
  • ที่เก็บข้อมูลตำแหน่ง (ตาราง driver_locations มีอยู่แล้ว — ปรับให้ผูกกับ "กล่อง/รถ")
  • ตารางจับคู่ "เลขกล่อง unit_id ↔ รถ (Truck)" — สำคัญมาก
  • หน้าจอแผนที่ real-time + สถานะ (เครื่องติด/ดับ, ความเร็ว, เวลาอัปเดต)
  • เก็บ API Key อย่างปลอดภัย (ไม่ commit ลงโค้ด)
⭐ 5.2 การจับคู่รถ (ต้องทำให้ครบก่อนใช้จริง): ข้อมูล GPS อ้างอิง เลขกล่อง และ ทะเบียนรถ แต่ระบบเราอ้างอิง "รถคันที่ X" → ต้องมีตารางจับคู่ จึงต้องขอ "รายการรถ + unit_id" จากผู้ให้บริการ (ส่วน 4)

5.3 ข้อมูลที่เราต้องส่งให้ผู้ให้บริการ

  • IP Address (สาธารณะ) ของ server เรา — กรณีต้อง whitelist
  • (ถ้าใช้แบบ B) URL ปลายทาง + Username/Password ที่เราออกให้

5.4 การตัดสินใจที่ CEO ต้องเคาะ

  • ความถี่อัปเดตที่ยอมรับได้ (เสนอ ~15–30 วินาที)
  • เก็บข้อมูลตำแหน่งย้อนหลังกี่วัน (เช่น 30/90 วัน)

6 รายการข้อมูลที่ต้องการ

อ้างอิงมาตรฐานกรมขนส่ง (DLT) เพื่อให้ผู้ให้บริการเทียบได้ว่า Pull API มี field เหล่านี้ครบไหม

ระดับField (DLT)ความหมายใช้ทำอะไร
ต้องมีunit_idเลขกล่อง GPSจับคู่ว่าเป็นรถคันไหน
ต้องมีlat, lonพิกัดปักหมุดบนแผนที่
ต้องมีutc_tsเวลาที่กล่องส่งตำแหน่งสดแค่ไหน
ต้องมีspeedความเร็วรถวิ่ง/จอด, เร็วเกินไหม
ต้องมีengine_statusเครื่อง ติด/ดับรถทำงานหรือจอด
อยากได้courseทิศทางวิ่งลูกศรหัวรถบนแผนที่
อยากได้ทะเบียนรถเลขทะเบียนจับคู่/แสดงให้คนอ่านง่าย
อยากได้fixสถานะสัญญาณพิกัดเชื่อถือได้ไหม
อยากได้mileageเลขไมล์สะสมดูระยะทางที่วิ่ง
มีก็ดีext_power_statusสถานะไฟเลี้ยงแจ้งเตือนกล่องถูกถอด
มีก็ดีover_speed_countครั้งขับเกินกำหนดความปลอดภัยคนขับ
มีก็ดีdriver_idรหัสใบขับขี่รู้ว่าใครขับ (ถ้ารูดบัตร)

หมายเหตุ: ถ้า Pull API ใช้ชื่อ field ต่างจากนี้ ขอเพียงระบุว่า field ไหน = ความหมายไหน ก็พอ

7 ขั้นตอนถัดไป

  1. เรา (Pooil): ส่งเอกสารนี้ให้ทีมเทคนิคผู้ให้บริการ
  2. ผู้ให้บริการ: ยืนยันแบบ A + ส่งมอบของในส่วนที่ 4 (เน้น: เอกสาร API + ตัวอย่าง + test account)
  3. เรา: ได้ test account → ทดสอบเรียก API จริง → ยืนยันดึงตำแหน่งได้ → สร้างหน้าจอแผนที่
  4. เรา: ขอรายการ "รถ ↔ unit_id" → ทำตารางจับคู่ → เชื่อมเข้าระบบจริง

📎 ภาคผนวก — ข้อมูลทางเทคนิค (อ้างอิงมาตรฐาน DLT)

เผื่อทีมเทคนิคผู้ให้บริการต้องการเทียบกับสิ่งที่ส่งกรมขนส่งอยู่แล้ว:

  • รูปแบบข้อมูล: REST + JSON (UTF-8)
  • โครงสร้าง: { vender_id, locations_count, locations:[ { unit_id, driver_id, seq, utc_ts, recv_utc_ts, lat, lon, alt, speed, engine_status, fix, license, course, hdop, num_sats, mileage, ext_power_status, over_speed_count, max_speed } ] }
  • พิกัด: ทศนิยมอย่างน้อย 5 ตำแหน่ง · เวลา: UTC ISO 8601 (เช่น 2016-01-07T22:13:56.504Z)
  • (แบบ B) Auth: Basic Authentication = base64(username:password) ใน Header Authorization: Basic <hash>
  • (แบบ B) Endpoint แนว DLT: POST /gps/add/locations → ตอบ { code:1, message:"ok", received_records:N }
