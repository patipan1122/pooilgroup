## 3. 🗣️ Debate Highlights (ทีมเถียงกันจริง)
1. **Model A (SKU ต่อหมวด) vs Model B (ใช้ JPS 3 ตัวของนักบัญชี)** → ทุกที่นั่งลงเอยที่ **B**. Model A = สร้างชุดสินค้าที่ 2 ซ้อนในสมุดเดียวกับที่นักบัญชีตั้งไว้แล้ว ผู้สอบบัญชีจะเห็น 2 ระบบ SKU ของของเดียวกัน + ต้อง backfill ที่ไม่มี.
2. **Devil กลับลำ** — R1 ค้านว่า "อย่าทำ settings เพิ่ม เปลือง" → R2 ยอมรับว่า dropdown 3 ตัวไม่ใช่ over-build แต่คือขั้นต่ำที่ทำให้ Model B เป็นจริง.
3. **CFO vs Devil เรื่อง GL** — Devil บอก "GL ติดมากับ SKU 3 ตัว พอแล้ว"; CFO ยืน "SKU(3) กับ GL เป็นคนละแกน งบจริงต้อง ~7-12 บัญชี ผู้สอบถึงอ่านได้". → **census ตัดสินด้วยข้อเท็จจริง API:** บรรทัด AP ไม่มี field `acc_buy` → GL รายหมวดทำได้ "ก็ต่อเมื่อ" TRCloud ยอมรับ acc_buy รายบรรทัด = **ต้องยิงทดสอบจริง 1 ใบก่อน** (เป็นคำถามเชิงทดลอง ไม่ใช่ความเห็น).
4. **ภาษีซื้อขอคืนไม่ได้** — CFO บอกเป็น "P0 live fix", Devil บอก "out of scope". census พิสูจน์ทั้งคู่ถูกครึ่ง: field `inputVatClaimable` มีอยู่แล้ว (schema:5348) แต่ **ไม่ถูกต่อเข้า push** + payload ฮาร์ดโค้ด `tax_report:'1'` ทุกใบ → แก้แค่ "เดินสายไฟ" field เดิม ไม่ต้อง workshop ใหม่.
5. **บล็อก vs ปล่อย+เตือน** เมื่อไม่มีสาขา → นักบัญชีหน้างาน + SA ดัน "บล็อก" (รายงานรายสาขาคือเหตุผลที่มีฟีเจอร์นี้); Devil + Architect ดัน "ปล่อย+เตือน อย่าขวางมือถือ" → ยกให้ CEO เคาะ.

## 4. ✅ Consensus Decisions (ทีมตกลงร่วมกัน)
- **D1 = Model B:** LedgerLine **ใช้** SKU JPS-100/101/103 ของนักบัญชี **ไม่สร้าง SKU เองอีกเลย** — ฆ่า path `resolveProductId` ที่ปั๊ม `LDG+sha1` ทิ้ง. รายละเอียดของจริงไปอยู่ใน "ชื่อบรรทัด" (free-text `product` ที่ส่งอยู่แล้ว line 338). ทะเบียนสินค้าแช่แข็งที่ ~3 แถว.
- **แกน SKU ≠ แกน GL** — SKU(3) = "เป็นของประเภทไหน", GL(`acc_buy`) = "ลงบัญชีค่าใช้จ่ายตัวไหนในงบ" ห้ามยุบรวมกัน.
- **จับคู่ทุกอย่างเป็น dropdown เท่านั้น** (หมวด→SKU, สาขา→department) ห้าม free-text → แอดมินพิมพ์ SKU/สาขาผิดเข้าสมุดร่วมไม่ได้.
- **สาขา→department มาจาก field ใหม่ต่อสาขา** ห้ามใช้ `Branch.code` (สแลก PO-FUEL-001) หรือ `Branch.name` ดิบ.
- **status='0' (บริการ/ไม่นับสต็อก) เป็น invariant** — LedgerLine ไม่แตะ stock ขาย (status=1) เด็ดขาด.
- **Snapshot** รหัส SKU/GL/department ลงบน LedgerExpense ตอน "ยืนยัน" → push เป็น serializer บริสุทธิ์ ไม่โดน race ตอนแก้ใบ/ลบสาขา (`onDelete:SetNull`, schema:5360).
- **อ่านค่าจริงจาก API ก่อนฮาร์ดโค้ด** — `inventory/list` + `department/list` บน company 31 (PDF manual ไม่ใช่ token จริง — เคยพังจาก SS260001 doubling).
- **Validator ครั้งเดียวตอนตั้งค่า** (เขียว/แดง "พบ/ไม่พบในระบบบัญชี TRCloud") ดีกว่า hard-gate 3 จุดตอน push — มือถือ confirm ลื่น + CEO เห็นสัญญาณภาษาคน.
- ทุกใบคงป้ายที่มา `ระบบบัญชี (LedgerLine) · อ้างอิง <docCode>`.

## 5. 🔗 Integration Map — เชื่อมของเดิมยังไง (additive ทั้งหมด)
**ตาราง/โมเดล:**
- `LedgerCategory` (5264): +`trcloudProductCode` (nullable, migration เพิ่ม 1 คอลัมน์, ปลอดภัย). `trcloudAccCode` มีอยู่แล้ว (5271).
- `Branch` (**SHARED** กับ FuelOS/ChairOps/repairs, schema:281): +`trcloudDept` — เลือกได้ระหว่าง `settings` JSON (ไม่ต้อง migration) หรือคอลัมน์ `trcloudDeptCode` (migration, nullable, ปลอดภัยเพราะโมดูลอื่นไม่อ่าน).
- `LedgerExpense` (5289): +3 snapshot cols (`trcloudProductCode/trcloudAccCode/trcloudDept`) stamp ตอนยืนยัน. `inputVatClaimable` (5348) มีแล้ว แค่ยังไม่ส่งเข้า push.
- `ledger_trcloud_product` (cache): ต้องล้าง/ข้ามแถว `LDG*` ตอน cutover ไม่งั้น cache hit จะปลุก SKU เก่าคืน.

**ไฟล์/flow:**
- `lib/ledger/trcloud-push.ts`: rewrite `resolveProductId` (253) → คืน bucket; ลบ `createInventory/searchInventoryByName/productCodeFor` ออกจาก push path; เพิ่ม `department` + `acc_buy` รายบรรทัด (เงื่อนไข) + ขับ `tax_report` จาก claimable; ขยาย `PushableExpense` (284).
- `app/(admin)/ledger/_actions.ts`: `loadPushable` (976) select branch + inputVatClaimable + trcloudProductCode + snapshots; `createCategory` (740) persist trcloudProductCode; validator ใหม่เรียก `inventory/list` + `department/list`.
- `app/(admin)/ledger/settings/_components/CategoryManager.tsx`: +dropdown SKU 3 ตัว + dropdown GL (จากผังบัญชี TRCloud).
- `app/(admin)/ledger/settings/_components/GroupBranchManager.tsx`: +field สาขา→department (**ไม่ใช่** `BranchPanel` — ตัวนั้นไม่มีจริง).
- `resolveLedgerPosting(expense)` ใหม่ ตอน "ยืนยัน": snapshot 3 ค่า + preflight gate.

**Migration-safety:** ทุกคอลัมน์ nullable additive → zero-downtime ไม่ต้อง backfill ไม่กระทบ /ledger เดิม และไม่กระทบ Branch ของโมดูลอื่น. ความเสี่ยง break จุดเดียว = ส่ง `department` ที่ TRCloud ไม่รู้จัก → กันด้วย rollout รายสาขา + omit เมื่อยังไม่ map. **ใช้ memory migration-trap:** apply migration เข้า prod DB ก่อน deploy โค้ด + deploy ด้วย isolated cherry-pick.

## 6. 🧩 Feature Spec (MoSCoW)
**MUST**
- D1 Model B: ฆ่า path ปั๊ม SKU `LDG+sha1`; อ้างอิง JPS-100/101/103 เท่านั้น
- +`LedgerCategory.trcloudProductCode` + dropdown 3 ตัวใน CategoryManager (dropdown only)
- อ่าน token SKU + ค่า department จาก `inventory/list` + `department/list` ก่อนฮาร์ดโค้ด
- ล้าง/ข้ามแถว `LDG*` ใน cache
- ต่อ `inputVatClaimable` → `PushableExpense` + `loadPushable` + ขับ `tax_report` (เลิกฮาร์ดโค้ด '1') — ปิดช่องภาษีซื้อขอคืนไม่ได้หลุดเข้า ภ.พ.30
- D3: +field สาขา→department ต่อสาขา + ส่ง `department` doc-level จาก `expense.branchId`; null→"สำนักงานกลาง"
- Snapshot 3 ค่า ตอนยืนยัน
- คง status='0' + source-tag
- **ยิงทดสอบจริง 1 ใบ** ยืนยัน TRCloud รับ `product_id=JPS-100` + ค่า department + (สำคัญ) `ap/create` รับ `acc_buy` รายบรรทัดไหม — ก่อน go-live

**SHOULD**
- อัปเกรด `trcloudAccCode` เป็น dropdown จากผังบัญชี TRCloud
- Validator ตอนตั้งค่า (เขียว/แดง พบ/ไม่พบ)
- Rollout `department` รายสาขา (omit สาขาที่ยังไม่ map)
- Hard-require `trcloudAccCode` ก่อน push (ถ้าเลือก GL รายหมวด)
- รายงาน reconcile ใบเก่า (null-GL/'00000'/LDG*) ให้คนตรวจ

**COULD**
- ป้ายเตือนบนจอ confirm มือถือเมื่อสาขาตกเป็น "สำนักงานกลาง"
- คอลัมน์จริง `Branch.trcloudDeptCode` (แทน settings-JSON)
- บัญชีพัก "รอจัดผังบัญชี" สำหรับหมวดยังไม่ map (แทนบล็อก)

**WON'T (นอกขอบเขตชัดเจน)**
- Model A (SKU ต่อหมวด ชุดซ้อน) — ปฏิเสธ
- สร้าง LedgerBranch / ตัวแก้ผังบัญชี ใน LedgerLine — บ้านของผังบัญชีอยู่ที่ TRCloud
- สคริปต์ลบ/แก้ใบ AP เก่าในสมุดร่วมอัตโนมัติ
- redesign UI ภาษีซื้อขอคืนได้/ไม่ได้ (เป็น workshop แยก) — แค่ต่อ flag เดิม
- แตะ stock ขาย (status=1)
- แตะ `customer.branch='00000'` (สาขาของผู้ขาย คนละ field)

## 8. ⚠️ Risks (Top)
- 🔴 **BLOCKING UNKNOWN:** `ap/create` อาจไม่รับ `acc_buy` รายบรรทัด → ถ้าไม่รับ GL รายหมวดทำไม่ได้ Q1 เหลือแค่ "3 GL หรือสร้าง SKU เพิ่ม" — **ต้องทดสอบจริง 1 ใบก่อนล็อก D2**

- ภาษีซื้อขอคืนไม่ได้หลุดเข้า ภ.พ.30 = ความเสี่ยงภาษีจริง วันนี้
