## 3. 🗣️ Debate Highlights — ประเด็นที่ทีมเถียงกันจริง

### 3.1 ประเด็นร้อนที่สุด: CEO เสนอ UI แบบ "เลื่อนข้อความยาวจนไม่อยากอ่าน แล้วค่อยติ๊กยินยอม"

**ทุกที่นั่งทั้ง 12 ปฏิเสธแนวคิดนี้เป็นเอกฉันท์** — แต่เหตุผลน่าสนใจกว่า "ไม่มีจริยธรรม":

- **ที่นั่งกฎหมาย (คำตัดสินหลัก):** การจงใจซ่อนเงื่อนไขในสัญญาสำเร็จรูป (contract of adhesion) **ไม่ได้ทำให้บังคับใช้ได้ง่ายขึ้น มันทำให้แย่ลง** — พ.ร.บ.ว่าด้วยข้อสัญญาที่ไม่เป็นธรรม พ.ศ.2540 ตีความข้อความไม่ชัดเจนให้เป็นคุณแก่ฝ่ายที่ไม่ได้ร่างสัญญาเสมอ และการซ่อนเจตนาอาจเข้าข่ายกลฉ้อฉลโดยนิ่ง (ป.พ.พ. ม.162) ยิ่งซ่อน ยิ่งเสี่ยงศาลตีเป็นโมฆะ ไม่ใช่น้อยลง
- **Devil's Advocate เสริมมุมที่คมกว่า:** ระบบดิจิทัลทิ้ง log ไว้ (ต่างจากกระดาษ) — ถ้าทนายฝ่ายลูกจ้างขอ log ออกมาโชว์ศาลว่า "ระบบถูกออกแบบมาให้กดยอมรับโดยไม่อ่าน" จะกลายเป็นหลักฐานเจตนาไม่สุจริตที่ยิ่งทำร้ายบริษัท — **แถมยังชี้ประเด็นที่ลึกกว่านั้น:** ถ้า audit trail ดีมากจนพิสูจน์ได้ว่า "อ่านและเข้าใจ" เงื่อนไขที่เนื้อหาเป็นโมฆะอยู่แล้ว (เช่น non-compete แบบกว้างเกินไป) จะยิ่งพิสูจน์ว่าบริษัท "รู้อยู่แล้วว่าเป็นโมฆะแต่ยังให้เซ็น" — **ต้องแก้เนื้อหาสัญญาให้ถูกกฎหมายก่อน แล้วค่อยสร้างระบบพิสูจน์การอ่าน ไม่ใช่กลับกัน**
- **UX/UI/End User (มุมออกแบบ+ผู้ใช้จริง):** candidate persona ยอมรับตรงๆว่าจะเลื่อนผ่านไม่อ่านเพราะกลัวดูมีปัญหา/เสียโอกาสได้งาน แล้วจะรู้สึก "โดนหลอก" ทีหลังถ้าเจอปัญหาจริง — ไม่ตอบโจทย์ที่ CEO ต้องการเลย (พิสูจน์ว่าเข้าใจจริง)
- **UI Designer:** ไม่มี pattern แบบนี้อยู่ในโค้ดเบสเลยสักที่ — การสร้างขึ้นมาคือของใหม่ที่ไม่ผ่าน "ต้องมีไหม" (ladder) ตั้งแต่ข้อแรก

**ทางออกที่ทีมสังเคราะห์ร่วมกัน** (ตอบโจทย์ CEO จริง — "พิสูจน์ได้ว่ารับทราบ" — ดีกว่าที่ CEO ขอมาด้วยซ้ำ): ดู Section 3.3

### 3.2 ระดับความหนักของ UI ต่อข้อ (UX หนัก vs QA/End User เบา)

- UX เสนอ Round 1: การ์ดแยก 3 ใบ + checkbox แยก + "พิมพ์ชื่อยืนยัน" ทุกข้อสำคัญ
- QA/QC เสนอ Round 1: ยุบสรุป+ขยาย+ tick เดียวจบ (เบากว่ามาก)
- End User (candidate persona) เตือนตรงๆ: "ถ้าเจอ checkbox 3 อันติดกันหนักเท่ากันหมด จะติ๊กผ่านตั้งแต่ใบที่ 2 โดยไม่อ่าน — กลายเป็นภาพลวงว่าอ่านแล้ว แย่พอๆกับ dark pattern เดิม แค่ดูดีกว่าทางกฎหมาย"
- UI Designer เสนอ (โดยไม่เห็นคำตอบ End User มาก่อน) แนวเดียวกัน: **น้ำหนัก UI ควรแปรตามความเสี่ยงทางกฎหมายจริงต่อข้อ** ไม่ใช่หนักเท่ากันหมด
- **Legal ตัดสินปิดประเด็น:** checkbox แยกรายข้อคือ**ขั้นต่ำที่บังคับทุกข้อ** (พิสูจน์ per-clause consent) แต่ "พิมพ์ชื่อยืนยันเข้าใจ" ไม่ใช่กลไกที่ถูกต้อง — พิมพ์ชื่อพิสูจน์แค่ "มีคนอยู่หน้าจอ" ไม่พิสูจน์ "เข้าใจ" ต้องใช้ **คำถามปรนัยสั้นถามผลกระทบจริง** (เช่น Yes/No) เฉพาะข้อที่เสี่ยงสูงสุด ส่วน "พิมพ์ชื่อ/initial" เก็บไว้ทำหน้าที่เป็นลายเซ็นอิเล็กทรอนิกส์ต่อข้อแทน คนละหน้าที่กัน

→ **สังเคราะห์สุดท้าย:** ทุกข้อมี checkbox แยก (บังคับ) + ข้อความเสี่ยงสูงสุดเท่านั้นที่เพิ่มคำถามปรนัย Yes/No + ทุกข้อ (รวม non-compete ถ้ามี) จบด้วย initial/ลายเซ็นต่อข้อ — ได้ทั้งความเข้มงวดทางกฎหมายและความเบาที่ candidate จะยังอ่านจริง

### 3.3 กลไกทดแทน dark pattern ที่ทีมลงตัว

รวมไอเดียจาก 6 ที่นั่ง (UI+UX+Legal+Architect+SA+QA) เป็นกลไกเดียว "Risk Summary Gate": หน้าสรุปความเสี่ยงแยกต่างหาก **โผล่ก่อนสัญญาเต็มทุกครั้ง** — reuse component `SignerRiskSummary` ที่มีอยู่แล้วจริงในโมดูล DocuFlow (การ์ดพับ/กาง 🟢🟡🔴) แต่ fork เป็น 2-3 การ์ดแยกรายข้อ + checkbox ของตัวเอง สัญญาเต็มยัง scroll ปกติและดาวน์โหลดได้ตลอด (ยิ่งเสริมว่า "ไม่ได้ถูกเร่งรีบให้เซ็น") ทุก interaction (กางอ่าน, เวลาที่ใช้, ติ๊ก, คำตอบคำถามรวมที่ตอบผิด, initial) เขียนลง `ConsentRecord` เดียวแบบ immutable ผูกกับ content-hash ของสัญญาที่เห็นจริง ณ วินาทีนั้น

### 3.4 การสร้าง User จริง — atomic-at-signing vs pending-verification-gate

ดูเผินๆเหมือนขัดกัน (SA/Architect ยืนกราน "ห้ามมี draft row" ส่วน BA/PM/Senior Programmer อยากได้ "HR confirm ก่อนเปิดสิทธิ์") — **แต่พิสูจน์แล้วว่าไม่ขัดกันเลย เป็นคนละมิติ:** สร้าง `User` row **ครั้งเดียว** ในทรานแซกชันเดียวกับตอนเซ็นสัญญาสำเร็จ (ไม่มี draft ก่อนหน้า — ตอบโจทย์ SA/Architect) แต่ column สถานะเริ่มต้นของแถวนั้นคือ `pending_verification` ทันที (ตอบโจทย์ BA/PM) — HR confirm คือการ UPDATE status ทีหลัง ไม่ใช่การ INSERT แถวใหม่

### 3.5 ขอบเขต non-compete และ Scope v1 vs v1.1

Project Owner + Devil's Advocate เสนอเลื่อนเงื่อนไข non-compete+ค่าเสียหายจริงไป v1.1 รอทนายแรงงานตรวจจริง — Legal ยืนยันหนักแน่นว่า blanket clause ("ที่เกี่ยวข้อง/แข่งขันใดๆ") ตามที่ CEO ร่างไว้ **มีความเสี่ยงสูงที่ศาลจะตีเป็นโมฆะทั้งข้อ** เพราะกว้างเกินไปและไม่มีค่าตอบแทน — เสนอแยก "ห้ามรั่วไหลความลับทางการค้า" (แข็งแรงอยู่แล้วตาม พ.ร.บ.ความลับทางการค้า 2545 ไม่ต้องพึ่งสัญญาเลย) ออกจาก "ห้ามไปทำงานคู่แข่ง" (อ่อนแอ ต้องแคบลงมาก) — **ทีมเห็นพ้องเลื่อน non-compete ไป v1.1** แต่ Legal + QA เตือนว่าแม้แต่เงื่อนไข "ปลอดภัยกว่า" ใน v1 (เลิกจ้างทดลองงาน + ย้ายที่ทำงาน) ก็ยังต้องมี carve-out ถูกต้องตามกฎหมาย (ไม่ตัดสิทธิ์ค่าชดเชย ม.118 / ค่าบอกกล่าวล่วงหน้า ม.17) ไม่งั้นทั้งข้อเสี่ยงเป็นโมฆะเหมือนกัน — **ต้องผ่านทนายตรวจแบบเบาคู่ขนานกับ engineering ไม่ใช่ข้ามไปเลย**

## 4. ✅ Consensus Decisions (ทีมตกลงกันแล้ว — ไม่ต้องรอ CEO)

1. **ปฏิเสธ dark-pattern UI โดยสิ้นเชิง** — ใช้ "Risk Summary Gate" แทน (Section 3.3)
2. **Reuse ของเดิม ไม่สร้างใหม่** (รายละเอียด Section 5):
   - ฟอร์มข้อมูล+เอกสาร → fork `app/apply/[slug]/apply-client.tsx` + `PublicFormRenderer` (**ไม่ใช่** `recruit-share` ซึ่งเป็นแค่หน้า list read-only — ทีมเข้าใจผิดตอนแรก แก้แล้วหลัง UI Designer เปิดโค้ดจริง)
   - การ์ดความเสี่ยง → fork `SignerRiskSummary` (DocuFlow)
   - หน้าเซ็น → fork `SignerInterface` (DocuFlow) ผ่าน route ใหม่ที่ตรวจสอบด้วยรหัสอ้างอิงแทน `requireSession()` (route เดิม `/sign/[placementId]` ล็อกด้วย session ใช้กับพนักงานใหม่ไม่ได้ — ต้องแก้ component ให้รับ `onSubmit` เป็น prop ~10 บรรทัด ไม่ใช่แค่ห่อ route) — "เซ็น" จริงคือพิมพ์ชื่อ+กดยอมรับ (CEO เลือก 2026-09-21) ไม่ใช่วาดลายเซ็น/OTP
   - เอกสาร → `Document`/`PersonDocument` models เดิม, **เก็บไฟล์ผ่าน Google Drive** ด้วย pattern `upload-drive` ที่ Recruit มีอยู่แล้วจริง (CEO ตัดสินใจ 2026-09-21 — ยกเลิกแผน R2 เดิม) **แต่แยก allowlist mime/size ใหม่เฉพาะเอกสารตัวตน** (ห้ามแก้ constant เดิมที่ /apply/[slug] ใช้งานจริงอยู่ — เจอ trap "แก้ของ generic กระทบหลายจุด" ก่อนเกิดจริง)
   - Draft autosave → localStorage pattern เดิม (`recruit_draft_${slug}`) แค่ re-key เป็น `_${referenceCode}`
3. **ตาราง staging ใหม่ที่ Recruit เป็นเจ้าของ** (ไม่แตะ User/PersonDocument จนกว่าจะจบ flow): `RecruitOnboardingInvite` (**referenceCode**/status/**issuedAt**/**supersededByCodeId** — ไม่มี `expiresAt` แล้วตาม decision 2026-09-21 ที่ CEO ต้องการลิงก์ถาวร) + `RecruitOnboardingDocument` (ไฟล์ staged, อ้างอิง Google Drive fileId แทน R2 key) + `RecruitOnboardingConsentRecord` (immutable, ต่อ interaction, ฟิลด์เซ็น = ชื่อที่พิมพ์+timestamp แทนรูปลายเซ็น) + `resultUserId` FK บน `RecruitApplication` (ตาม pattern `RegisterRequest.resultUserId` ที่มีอยู่แล้ว)
4. **User creation = atomic ที่จุดเซ็นสัญญาสำเร็จ, born `pending_verification`** — ไม่มี draft row ก่อนหน้า, auth guard กลางของระบบ (ไม่ใช่แค่ Recruit) ต้องเช็ค status นี้ก่อนปล่อย login
5. **(อัปเดต 2026-09-21) Regenerate รหัสอ้างอิง = supersede เสมอ ไม่ใช่ silent revoke/silent duplicate** — ลิงก์เป็นอันเดียวถาวรแล้ว ไม่มี "regenerate link" อีกต่อไป แต่ยังต้อง regenerate **รหัสอ้างอิง**ได้ถ้ารหัสเดิมหลุด/พิมพ์ผิดส่งไปให้คนอื่น — DB partial unique index กันมีรหัส active ซ้ำต่อ applicant, เอกสารที่อัปโหลดค้างไว้ถูกย้ายไปผูกกับรหัสใหม่อัตโนมัติ (ไม่ต้องอัปซ้ำ), รหัสเก่าที่ถูกแทนที่ใช้กรอกต่อไม่ได้ (โชว์ข้อความ "รหัสนี้ถูกยกเลิกแล้ว")
6. **Contract template ต้อง version + content-hash-snapshot ทุกครั้งที่เซ็น** — หน้าจอที่ candidate เห็นตอนเซ็นต้อง render จาก snapshot จริง ไม่ใช่ query template ปัจจุบัน (กัน template เปลี่ยนย้อนหลังกระทบสัญญาเก่า)
7. **Sign→create-User boundary = 1 DB transaction + idempotency key จาก DocuFlow signing-event-id** (กัน webhook redelivery สร้างพนักงานซ้ำ — จุดเสี่ยงที่ไม่มีใครเห็นจนรอบ 2)
8. **(สำคัญขึ้นมากหลัง decision 2026-09-21) URL ถาวรใหม่ต้องมี rate-limit/anti-brute-force บนช่อง "รหัสอ้างอิง" อย่างเข้มงวด** — เพราะ URL เองเป็นสาธารณะและถาวร ไม่หมดอายุ ไม่มี `requireSession()` คุ้มกันเหมือนจุดอื่นในระบบ ตัวรหัส 6 หลักคือด่านป้องกันเดียว: ต้อง lock หลังกรอกผิดติดกันไม่กี่ครั้ง (เช่น 5 ครั้ง/ชม./IP) + log ทุกครั้งที่กรอกผิด + แจ้งเตือน HR ถ้ามีความพยายามกรอกผิดผิดปกติต่อ applicant เดียว (สัญญาณว่ารหัสอาจหลุด)
9. **Age-gate:** เก็บวันเกิดในฟอร์มข้อมูลทั่วไป (ไม่ทำหน้าแยก) คำนวณอายุอัตโนมัติ **&lt;18 ปีตัดออกจาก self-service ทันที** ส่งเข้ากระบวนการ HR ทำมือ (กฎหมายแรงงานมีภาระหลายข้อที่ digital self-service ทำแทนไม่ได้ — แจ้งพนักงานตรวจแรงงาน 15 วัน, ห้ามงานอันตราย/กลางคืน/OT, ต้องขอ guardian consent ซ้อนสำหรับข้อมูลส่วนบุคคล)
10. **รูปบัตรประชาชน = ข้อมูลอ่อนไหวตาม PDPA ม.26** (มีช่องศาสนาพิมพ์บนบัตร) — ต้องมี consent แยกต่างหากจาก consent สัญญาทั่วไป (การค้นพบใหม่จาก Legal ที่ไม่มีใครเห็นมาก่อน)
11. **HR dashboard แบบเบาต้องอยู่ใน v1 ไม่ใช่ตัวเลือก** — list + status (SENT/IN_PROGRESS/SIGNED/COMPLETED/EXPIRED/DECLINED) + ปุ่ม resend เดียว — ทุกที่นั่งที่จำลอง HR ยืนยันตรงกันว่าไม่มี = เลิกใช้กลับไปกระดาษ = ROI ทั้งฟีเจอร์เป็นศูนย์
12. **ไม่ต้องออกแบบ schema เผื่อ employee-master-table ในอนาคต** — staging-table design แยก write-boundary เป็นจุดเดียวอยู่แล้ว พอสำหรับต่อยอดในอนาคตโดยไม่ต้อง migrate ใหม่ (Project Owner ถอนคำขอเดิมหลังฟัง Architect)
13. **(อัปเดต 2026-09-21) Cron "onboarding janitor" รายวัน** — ไม่มี "ลิงก์หมดอายุ" ให้ flip อีกต่อไป (ลิงก์ถาวร) แต่ยัง flip รหัสอ้างอิงที่ **ค้างไม่มีความเคลื่อนไหวเกิน N วัน** (proposed 30 วัน) เป็น STALE + ลบเอกสาร/แถวที่ค้าง (retention, ดู decision D), ยิง reminder ให้ HR ถ้ารหัสที่ออกไปแล้วยังไม่มีคนกรอกเกินกำหนด

## 6. 🧩 Feature Spec (MoSCoW)

### Must (v1)
- HR กดปุ่ม "คอนเฟิร์มรับพนักงาน" บน applicant สถานะ HIRED → ระบบออกรหัสอ้างอิง 6 หลักใหม่ (ลิงก์เองเป็น URL ถาวรอันเดียวที่ไม่ต้องสร้างใหม่) → HR ส่งลิงก์+รหัสให้ candidate
- Candidate เปิดลิงก์ถาวร → กรอกรหัสอ้างอิงยืนยันตัวก่อน → กรอกข้อมูลจริง + อัปโหลดเอกสารประจำตัว (เก็บเข้า Google Drive) ผ่านฟอร์ม (fork จาก apply/slug)
- Age-gate อัตโนมัติจากวันเกิด — &lt;18 ตัดออกจาก self-service
- Consent แยกสำหรับข้อมูลอ่อนไหว (รูปบัตร ปชช.) แยกจาก consent ทั่วไป
- Risk Summary Gate (2-3 การ์ดตามเงื่อนไขจริงที่ตัดสินใจไว้ v1: ทดลองงาน+เลิกจ้างได้ (มี severance/notice carve-out) + ย้ายที่ทำงาน (มีขอบเขต) + confidentiality/trade-secret) ก่อนสัญญาเต็มเสมอ — checkbox แยกทุกข้อ + คำถามปรนัยเฉพาะข้อเสี่ยงสูงสุด
- เซ็นสัญญาผ่าน DocuFlow signature engine (ผ่าน wrapper route ใหม่) — "เซ็น" คือพิมพ์ชื่อ-นามสกุล+กดยอมรับ (CEO เลือก 2026-09-21 — เบาที่สุด ไม่มีวาดลายเซ็น/OTP)
- `ConsentRecord` immutable ต่อทุก interaction พร้อม content-hash ของสัญญาที่เห็นจริง
- User สร้าง atomic ตอนเซ็นเสร็จ, born `pending_verification`, HR confirm ก่อนเปิด login
- HR dashboard เบา: list + status + resend (supersede)
- Onboarding janitor cron: expire ลิงก์, purge ข้อมูลค้าง, reminder ก่อนหมดอายุ
- Light legal review (ทนายแรงงาน) ของ clause ที่ใช้ใน v1 ก่อนปล่อยใช้งานจริง

### Should (v1, ถ้าเวลาเอื้อ)
- Comprehension คำถามปรนัยครอบคลุมทุกข้อ (ไม่ใช่แค่ข้อเสี่ยงสูงสุด)
- Reminder อัตโนมัติ 48 ชม. ก่อนลิงก์หมดอายุ

### Could (v1.1)
- เงื่อนไข non-compete + ค่าเสียหายจริง (รอทนายแรงงานตรวจเต็มรูปแบบ, ขอบเขตแคบลงตามคำแนะนำ Legal)
- OTP-verified e-signature (ยกระดับความแข็งแรงถ้ามีข้อพิพาท/fraud จริงเกิดขึ้น)
- Full analytics/reporting dashboard สำหรับ HR
- Employee-master-table เต็มรูปแบบ (ถ้า requirement จริงเกิดขึ้น)

### Won't (v1)
- ดึงข้อมูล/เอกสารจากใบสมัครเดิมมาใช้ซ้ำ (CEO ปฏิเสธตั้งแต่ต้น)
- Dark-pattern UI ทุกรูปแบบ
- Payroll sync / access provisioning / org chart integration

### Edge cases (Top 10)
1. HR regenerate รหัสอ้างอิงซ้ำ (รหัสเดิมหลุด/พิมพ์ผิด) → supersede ไม่ใช่ revoke เงียบ, เอกสารเดิมย้ายไปผูกรหัสใหม่
2. Candidate ปิดแท็บกลางคัน → resume ด้วยรหัสอ้างอิงเดิม (auto-save)
3. เซ็นสำเร็จแต่สร้าง User ล้มเหลว (หรือกลับกัน) → 1 transaction กัน half-state, reconciliation queue ให้ HR เห็น
4. Webhook จาก DocuFlow ยิงซ้ำ → idempotency key กันสร้าง User ซ้ำ
5. ผู้สมัครอายุ &lt;18 → route ไป HR manual process
6. เอกสารเบลอ/ไฟล์ปลอมนามสกุล → MIME sniffing จริง, ไม่เชื่อ extension
7. Candidate เซ็นแล้วไม่มาทำงานจริง → retention clock แยก (สั้นกว่าพนักงานจริง, decision D)
8. Template สัญญาเปลี่ยนระหว่างทาง → content-hash snapshot กันกระทบสัญญาเก่า
9. รหัสอ้างอิง 6 หลักถูกเดา/brute-force → rate-limit เข้มงวดบน URL ถาวร (จุดป้องกันเดียวเพราะไม่มี expiry ช่วย)
10. ปุ่ม "แตะเพื่อเซ็น" ต้อง disabled จนกว่าจะติ๊กครบทุกการ์ดเสี่ยง (**พบว่าโค้ดต้นแบบ SignerInterface ไม่มีเงื่อนไขนี้เลย — ต้องเพิ่ม prop `canSign` ไม่งั้นการ์ดทั้งหมดเป็นแค่ของประดับ**)

1. 🔴 เนื้อหาสัญญา (แม้แต่ clause "ปลอดภัย") ไม่ผ่านทนายจริงก่อนปล่อยใช้งาน → ทุกสัญญาที่เซ็นตั้งแต่วันแรกเสี่ยงเป็นโมฆะพร้อมกันหมด
2. 🔴 ปุ่มเซ็นไม่ถูกผูกเงื่อนไขกับการ์ดความเสี่ยง (ต้อง wire `canSign` prop จริง ไม่ใช่แค่ออกแบบสวยๆ)
3. 🟡 URL onboarding ถาวรใหม่ไม่มีการป้องกัน brute-force/rate-limit บนรหัสอ้างอิงตั้งแต่ day 1 (สำคัญกว่าที่ประเมินไว้ตอนแรก เพราะไม่มี TTL ช่วยจำกัดเวลาโจมตีแล้ว)
4. 🟡 สร้างของที่ HR ไม่ใช้จริง (ไม่มี dashboard หรือ hiring volume ต่ำเกินจะคุ้ม) — ดู decision A
5. 🟢 เอกสารส่วนบุคคลอ่อนไหวรั่วไหล/ค้างไม่มีวันลบ — ลด risk แล้วด้วย retention cron + consent แยกสำหรับข้อมูลอ่อนไหว

**Out of Scope (v1):** payroll sync, org chart, access provisioning อัตโนมัติ, non-compete+ค่าเสียหายจริง, full analytics, OTP signature
