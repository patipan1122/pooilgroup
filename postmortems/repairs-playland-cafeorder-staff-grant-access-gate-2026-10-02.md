# Repairs / Playland / CafeOrder — staff with an admin-tier module grant still bounced from admin pages

**Summary.** Same bug class as `staff-invite-grant-access-gate-2026-09-30.md` (DocuFlow, fixed earlier the same day): `inviteProgramStaff()` can mint a plain org-role `staff` user plus a `user_modules` grant for one program, and a program admin can additionally promote that grant to `role='admin'` to hand the staff member full control of their one program. DocuFlow's fix added two shared composed helpers in `lib/auth/module-access.ts`. Repairs, Playland, and CafeOrder don't use those shared helpers at all — each keeps its own local, hand-rolled role-array system (`REPAIR_ADMIN_ROLES`, `PLAYLAND_ADMIN_ROLES`, `CAFE_ADMIN_ROLES`), so a `staff` + admin-tier-grant combo was invisible to all three, independently of the DocuFlow fix. Fixed by composing each module's own admin-tier check with `userIsModuleAdmin(user, "<slug>")` — same pattern, applied at each module's actual architectural seam (which turned out to be a different file per module; see Root cause). View/cashier-tier access (already working for `staff` via each module's `*_ROLES` array) and every existing role-tier user's behavior are untouched.

## Symptom

Confirmed live before the fix, by direct code read (not yet click-tested at the time of the investigation this fix is based on):

- Repairs: a `staff` user holding a `user_modules.role='admin'` grant for `repairs` was bounced from `/repairs/settings`, `/repairs/technicians`, `/repairs/categories` (redirected to `/repairs`).
- Playland: same shape — bounced from `/playland/settings`, `/playland/audit`, `/playland/overrides` even with an admin-tier grant.
- CafeOrder: `CAFE_MANAGER_ROLES` doesn't include `staff` at all (unlike the other two), so a staff+admin-grant combo would fail even basic menu management (`createCategory`, `toggleTechnicianActive`-equivalent actions), not just the stricter `CAFE_ADMIN_ROLES` tier.

View/cashier-tier access for a `staff` user was already correct in all three (each module's base `*_ROLES` array already lists `staff`) — only the admin tier (and, for CafeOrder, the manager tier too) had the gap.

## Root cause

All three modules predate `userIsModuleAdmin`/the `inviteProgramStaff()` grant-promotion flow and implement authorization as a flat `DbUser["role"][]` array plus a plain `.includes(role)` check — no path to consult `user_modules` at all. But the actual *fix point* differs per module because each one wraps that role check differently:

1. **Repairs** (`lib/repair/role-guard.ts`) — `canRepairAdmin`/`requireRepairAdmin` took a bare `role: DbUser["role"]` and every call site passed `session.user.role` directly. Fix point: the functions themselves, widened to take the full `DbUser` (needed because `userIsModuleAdmin` reads `.org_id`/`.id` too, not just `.role`).

2. **CafeOrder** (`lib/cafeorder/role-guard.ts`) — identical shape to Repairs: `canCafeManage`/`canCafeAdmin` took a bare `role`, called directly as `canCafeManage(session.user.role)` from 3 call sites (`lib/cafeorder/menu-actions.ts:20`, `lib/cafeorder/import-actions.ts:14`, `app/api/cafeorder/menu/template/route.ts:28`). Same fix shape as Repairs.

3. **Playland** (`lib/playland/role-guard.ts` + `lib/playland/position-resolve.ts`) — architecturally different, and the real reason this module needed investigation before fixing. Playland layers a SECOND authorization system on top: `playlandStaffBranch` assigns each staff member a per-branch "position" (`owner`/`manager`/`cashier`), and `getPlaylandRole(userId, orgId, orgRole)` resolves that into a *synthetic* `DbUser["role"]` (`owner`→`"admin"`, `manager`→`"branch_manager"`, `cashier`→`"staff"`) which every single call site — all ~46 of them, in both `app/(admin)/playland/**` and `lib/playland/**` — passes into the existing `canPlaylandAdmin`/`canPlaylandManage`/`requirePlaylandAdmin`/etc. functions *instead of* the user's real role. Grepping confirmed **zero** call sites anywhere in the module call `canPlaylandAdmin`/`requirePlaylandAdmin` with a raw `session.user.role` — every one goes through `getPlaylandRole()` first. That means widening `canPlaylandAdmin`/`role-guard.ts` itself (the Repairs/CafeOrder-style fix) would have been unreachable dead code: no call site has a raw `DbUser` to hand it once `getPlaylandRole()` has already collapsed it to a role string. The actual fix point is `getPlaylandRole()` itself.

## Playland branch-position investigation result (scoped-in this round)

A prior investigation pass flagged "does the position system interact with or bypass the admin-tier gate?" as out of scope. Investigated now:

- **The position system cannot substitute for module entry.** `playland/layout.tsx` gates entry with `isAdminTier(role) || userHasModuleAccess(user, "playland")` *before* `getPlaylandRole()` is ever called. A user with a `playlandStaffBranch` position but **zero** `user_modules` grant is bounced at `/403` before the position is ever read — confirmed via headless click-through (see Validation). This is pre-existing, correct, unrelated-to-this-fix behavior, not a gap.
- **The position system and the new grant-admin elevation are independent, non-conflicting paths to the same synthetic `"admin"` outcome**, both gated behind the same entry requirement above. Once a user has module entry (grant or admin tier), `getPlaylandRole()` now checks, in order: (1) real admin-tier role → return as-is; (2) `user_modules.role==='admin'` grant for `"playland"` → return synthetic `"admin"` (the fix, new); (3) highest `playlandStaffBranch` position → map to synthetic role (pre-existing, unchanged); (4) fall back to the org-wide role. An admin-tier grant always wins over a lower branch position if a user somehow has both, which is the correct precedence (grant is explicit elevation; position is a workspace-tier default).
- **No interaction/bypass risk found.** The two systems don't read or write each other's data, and a member-tier (non-admin) grant does not affect position resolution at all, since `userIsModuleAdmin` only matches `role==='admin'` specifically.

## Why it slipped through

Same reason as the DocuFlow case: `tsc`/`eslint`/`next build` all pass regardless — every call site is type-correct, the gap is a logical role-vs-grant mismatch only visible by actually impersonating an affected user and clicking through. Additionally, for Playland specifically, a naive fix (editing `role-guard.ts`'s `canPlaylandAdmin` to accept a `DbUser` like Repairs/CafeOrder) would have *looked* correct (compiles, passes `role-gate-completeness`) while being completely inert — every call site would still be feeding it a role string, not a user object. This was only caught by grepping every call site before writing the fix, per the task's explicit instruction to investigate the position system rather than guess.

## Fix

**Repairs** (`lib/repair/role-guard.ts`): `canRepairAdmin`/`requireRepairAdmin` widened from `(role: DbUser["role"])` to `(user: DbUser)`, composed as `REPAIR_ADMIN_ROLES.includes(user.role) || (await userIsModuleAdmin(user, "repairs"))`. 5 call sites updated to pass `session.user` and `await` the now-async functions: `app/(admin)/repairs/settings/page.tsx:28`, `app/(admin)/repairs/technicians/page.tsx:13`, `app/(admin)/repairs/categories/page.tsx:13`, `app/(admin)/repairs/triage/page.tsx:86`, `app/(admin)/repairs/[id]/page.tsx:32`, plus 4 sites in `lib/repair/actions.ts` (lines 281, 838, 869, 924 — `CLOSED` transition, `createTechnician`, `toggleTechnicianActive`, `createCategory`). `canRepairWrite`/`REPAIR_WRITE_ROLES` (unaffected tier) left untouched.

**CafeOrder** (`lib/cafeorder/role-guard.ts`): both `canCafeManage` and `canCafeAdmin` (+ their `require*` wrappers) widened the same way, each composed with `userIsModuleAdmin(user, "cafeorder")`. `canCafeManage` is fixed because `CAFE_MANAGER_ROLES` excludes `staff` entirely (unlike the other two modules' manager/write tiers) — without this, an admin-grant staff member would fail even basic menu management, not just the stricter admin tier. 3 call sites updated: `lib/cafeorder/menu-actions.ts:20`, `lib/cafeorder/import-actions.ts:14`, `app/api/cafeorder/menu/template/route.ts:28`. `canCafeAdmin`/`requireCafeAdmin` fixed at the same time even though no call site uses them yet (no settings/points-policy page exists) — correct from day one for when one is built.

**Playland** (`lib/playland/position-resolve.ts`): `getPlaylandRole()` now runs `userIsModuleAdmin(grantUser, "playland")` in parallel with the existing `playlandStaffBranch` lookup (`Promise.all`, no added latency over the pre-existing query), and returns synthetic `"admin"` immediately if it matches — checked *before* falling back to the position-derived role, so an admin-tier grant always wins regardless of branch position. `grantUser` is a `DbUser`-shaped object built from the 3 primitives `getPlaylandRole()` already receives (`userId`/`orgId`/`orgRole`), with the unused `DbUser` fields filled with inert defaults (`email: null`, `name: ""`, etc.) — `userIsModuleAdmin` only reads `.id`/`.org_id`/`.role`, so this satisfies the full type without an unsafe cast. **Zero of the ~46 call sites across the module needed to change** — this is the one choke point every one of them already flows through, which is exactly why fixing it here (not in `role-guard.ts`) makes the fix reachable at all. `role-guard.ts`'s `canPlaylandAdmin`/`requirePlaylandAdmin`/`PLAYLAND_ADMIN_ROLES` themselves are untouched.

All three reuse the existing `userIsModuleAdmin` from `lib/auth/module-access.ts` (no new auth primitive, no duplicated grant-matching logic) — the same composition pattern already established for DocuFlow and the ~15 RentSpace/ChairOps/ClawHub "ALREADY-CORRECT-COMPOSED" sites in `lib/auth/role-gate-known-exceptions.ts`.

### Gotcha found while validating (harness, not product bug)

`requireRepairAdmin`'s `redirect("/repairs")` (and `requirePlaylandAdmin`'s `redirect("/playland")`) fire from inside the **page** component, after the parent layout has already started streaming its 200 response — Next.js can't change the HTTP status at that point, so it delivers a client-side ("soft") redirect inside the RSC payload instead of a clean top-level 307. A test that reads `page.url()` right after `domcontentloaded` catches the stale pre-redirect URL/status and misreports PASS as FAIL. Fixed by waiting for `networkidle` before reading the final URL. Entry-level redirects (`/403`, thrown from the layout before any child starts rendering) were unaffected by this and read correctly either way — worth remembering for any future Playwright regression test against a **page-level** (not layout-level) `redirect()` in this codebase.
