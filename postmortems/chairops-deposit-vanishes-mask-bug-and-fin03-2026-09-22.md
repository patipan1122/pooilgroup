# Post-mortem: ChairOps deposits "vanish" from the branch shortage number after slip attach

**Summary.** Branch staff submitted deposits with a slip attached and saw a normal success confirmation, but the branch's shortage number ("เงินขาด") did not reflect the deposit, and the reconcile page's "สลิป" cell showed a red flag with no explanation. Two independent, compounding causes: (1) `checkSlipFraud`'s masked-bank-account comparison used `endsWith()` instead of `includes()`, wrongly flagging deposits at banks whose slip format masks the *middle* digits rather than the leading ones (fix built 2026-09-20, sat undeployed for 2 days); (2) the 2026-09-20 "FIN-03" change intentionally excluded any `requiresReview=true` deposit from the branch shortage number until office cleared it, but shipped with zero visual signal to branch-level roles — a flagged deposit looked identical to money that never arrived. Fixed by deploying the already-tested mask fix (commit `8d516ebe`) and, per a same-day CEO decision, reverting FIN-03's hold-out on the shortage number while adding a color-coded review-status badge to the deposit the maid can see (commit `8932a569`, comment cleanup `c967e561`). All three commits deployed live 2026-09-22.

**Symptom.** CEO report: "พนักงานกด ยอดฝาก กดฝากเงินไปแล้ว แต่เงินไม่โผล่ในช่องฝากเงิน" + "พนักงานกดฝากเงินแนบสลิปไปแล้วทำไม ไม่ขึ้น" — no branch, deposit ID, or screenshot given; investigation had to establish the mechanism from code + live data rather than a single reproducible case.

**Root cause (two, compounding).**

*Cause 1 — masking-position bug, still live in production.* `checkSlipFraud` (`lib/chairops/reconcile/slip-ocr.ts:249`, pre-fix) compared the OCR-read masked bank account digits against the branch's configured account using `a.endsWith(b) || b.endsWith(a)`, assuming slip masking always hides leading digits and reveals the trailing ones. At least one bank's slip format instead reveals the *middle* digits (e.g. configured `8134350838`, OCR reads a mask exposing `...5083...`, positions 5-8, not the tail `0838`) — `endsWith()` never matches, so `requiresReview` gets set `true` on an entirely correct deposit. This exact bug and fix were identified, built, and validated against 60 days of real data two days earlier ([[chairops-slip-account-mask-false-positive-2026-09-20]]) but the branch (`claude/chairops-slip-mask-fix-2026-09-20`, commit `7b56df99`) was never merged — it sat on `origin/setup` waiting for a deploy decision that hadn't come up again until this report surfaced it.

*Cause 2 — FIN-03's hold-out had no branch-facing signal.* `lib/chairops/reconcile/drift-engine.ts` (both `computeDriftMoneyAsOf` at line 159 and the window-mode formula at line 334) and `lib/chairops/queries/_deposits.ts:55` (`buildDepositWhere`) all filtered `requiresReview: false` when summing deposits — a deliberate 2026-09-20 CEO decision (FIN-03) to stop a flagged/unverified amount from silently zeroing out a branch's apparent shortage before office confirmed it. This is correct in intent, but the maid's own deposit-confirmation flow (`app/(admin)/chairops/(maid)/m/collect/[id]/page.tsx`, pre-fix) showed a plain green "ฝากแล้ว" card regardless of `requiresReview`, and no other branch-facing surface showed a pending/flagged state at all. The only place `requiresReview=true` deposits were visible was `/chairops/review-queue`, gated `requireRole("OFFICE")` — invisible to `MAID` role entirely.

**Why it produced the symptom.** A maid at an affected branch submits a deposit → `checkSlipFraud` (inside an `after()` callback, running after the deposit row is already durably committed — confirmed no data loss, see Validation) wrongly flags it via Cause 1 → the branch shortage number silently excludes it via Cause 2 → the maid sees "บันทึกแล้ว ✓" as always, but the branch-level number a manager or office checks doesn't move, and the "สลิป" cell on the reconcile page shows red with no further explanation to anyone below OFFICE role. Two independently-shippable, individually-reasonable changes (a fraud-detection heuristic bug, and a deliberate money-safety hold-out) combined into a confusing, trust-eroding "your deposit vanished" experience.

**Fix.**
1. Deployed the already-validated `endsWith()`→`includes()` fix (`lib/chairops/reconcile/slip-ocr.ts:249`, commit `8d516ebe`, merging `claude/chairops-slip-mask-fix-2026-09-20`). No behavior regression: `includes()` is a strict superset of the old `endsWith()` match.
2. Per explicit CEO decision (asked directly, not assumed — money-calculation changes need owner sign-off in this codebase): reverted FIN-03's `requiresReview: false` filter in all three locations (`drift-engine.ts` ×2, `_deposits.ts` ×1) so a deposit counts into the shortage number the instant it's submitted, restoring pre-2026-09-20 behavior. Commit `8932a569`.
3. Added a visible review-status signal on the one branch-facing deposit view that exists (`m/collect/[id]/page.tsx`): the deposit-confirmation card and status badge now render red ("ฝากแล้ว · รอตรวจสอบ" + an explanatory line "office กำลังตรวจสอบสลิปนี้ — ยอดนับรวมในระบบแล้ว") when `requiresReview=true`, green otherwise — reusing the existing `Badge` component's `tone="danger"`/`"success"` already used elsewhere in the app, same commit.
4. Fixed a stale code comment on `/chairops/review-queue` (`app/(admin)/chairops/(office)/review-queue/page.tsx`) that still described the now-reverted hold-out behavior (commit `c967e561`).

Ledger-push (`lib/chairops/reconcile/ledger-push.ts`, syncing to LedgerLine's `ledger_revenue_entry`) and the office LINE alert on flagged deposits (`app/(admin)/chairops/collect/actions.ts:612-626`) both still filter/trigger on `requiresReview` and were deliberately left unchanged — those are separate concerns (external accounting sync, office notification) not covered by the CEO's decision, which was scoped to the branch-facing shortage number and deposit view only.

**How it was found.** CEO's report was investigated via a read-only agent that (a) traced the maid deposit flow end-to-end confirming the money-write itself is synchronous and safe, (b) read the FIN-03 diff to find exactly which surfaces stop showing a flagged deposit, and (c) queried `ChairopsCashDeposit` via the `weekly_health_check_ro` role for the last 3 days' `requiresReview=true` rows, cross-checking each OCR-read account fragment against the branch's configured number. 12 of an initial 18 flagged rows matched the exact masking-middle signature; a follow-up query after the first deploy found the count had grown to 18 (15 masking-pattern, 3 genuine mismatches), confirming the bug was still actively producing false positives in real time, not just historically.

**Why it slipped through.** Two separate gaps: (1) the mask-position fix was built and validated 2026-09-20 but deployment requires explicit CEO go-ahead per this repo's standing rule, and no one re-raised it for two days until the downstream symptom surfaced independently; (2) FIN-03 was reviewed and approved for its money-safety property but the UX consequence (a flagged deposit becomes invisible to the role who submitted it) was not caught before shipping — no branch-facing surface was audited for "what does a flagged deposit look like to a maid" as part of that change.

**Validation.** `tsc --noEmit`: 0 errors on every commit. `eslint` on all touched files: 0 errors. `next build`: succeeded for all routes on all three commits. `git status --porcelain`: clean after each commit. Live smoke test after each of the three deploys: new Vercel deployment confirmed via a changing `dpl_` response-header fingerprint, then `/`, `/login`, `/chairops`, `/chairops/reconcile/2aa1207b-dc2a-4135-982e-a0e217789b06` all returned expected 200/307 with no 500s. Deposit-write safety was confirmed by code inspection (the `$transaction` creating the `ChairopsCashDeposit` row is fully awaited before the `after()` block that runs `checkSlipFraud`/OCR/Drive-backup — no half-written state possible). Not validated: an actual authenticated in-app click-through by a maid or office user (unauthenticated `curl` cannot observe post-auth-guard rendering) — pending CEO/staff confirmation in the field. Also not validated: whether the shortage-number swing from including the 15 now-recognized-as-legitimate deposits (~฿20,780 across 8 branches, per the pre-fix query) matches office's own expectations once they see it — no explicit before/after dollar comparison was run against a specific branch's dashboard.

**Action items / follow-ups.**
- 15 already-flagged deposits from before the mask-bug fix remain `requiresReview=true` in the database (deploying code never retroactively re-evaluates existing rows) — office must manually clear each via the "ตรวจแล้ว" button on `/chairops/review-queue` (one at a time, no bulk action exists). CEO informed directly; no automated backfill was run (would require prod DB write access this session doesn't hold without live authorization).
- Three other office-facing deposit-list surfaces identified during investigation still lack a `requiresReview` badge despite not filtering the rows out (`getReconcileDayDetail` day-drawer and `getReconcileActivity` timeline in `lib/chairops/queries/reconcile-v2.ts`, and the cross-branch `/chairops/collections` history page) — left out of this fix's scope since they're OFFICE-role, not branch-facing, and CEO's decision was specifically about what branch staff see. Not filed as a ticket; noted here for whoever next touches those pages.
- No bulk "clear all confirmed-safe flags" action exists on `/chairops/review-queue` — would reduce office's manual-click burden the next time a detection bug produces a batch of false positives. Not filed as a ticket; flagged as a forward-looking note only, since this is the first time it's mattered at this scale.
