# Post-mortem: ChairOps slip account-number check misses middle-masked slips

**Summary.** `checkSlipFraud` in `lib/chairops/reconcile/slip-ocr.ts` compares a deposit slip's OCR-read (masked) bank account number against the branch's configured account number using `endsWith()`, which assumes bank slips always mask the leading digits and reveal the trailing ones. At least one real slip masking format instead reveals the *middle* digits, so `endsWith()` never matches and every deposit at the affected branches gets flagged `requiresReview` as a possible wrong-account fraud, even though the account is correct. Confirmed across 16 branches via a 60-day read-only DB sweep. Fixed by switching the comparison to `includes()`, which matches the visible digits at any position in the full number. Branch `claude/chairops-slip-mask-fix-2026-09-20`, commit `7b56df99`. Not yet merged to `setup` / deployed — pending CEO go-ahead.

**Symptom.** CEO screenshot of `/chairops/reconcile/<branchId>` for "คอนโด เคนซิงตัน สุขุมวิท (350)" (`branchId = 2aa1207b-dc2a-4135-982e-a0e217789b06`) showed the "สลิป" column red/flagged for all 13 visible daily rows (2026-09-07 → 2026-09-20). A 30-day sweep of `chairops."ChairopsCashDeposit"` found the identical pattern in 16 branches total (e.g. Kensington Condo 20×, Indexบางนา 17×, ฟิวจันทร์สาธร 13/13).

**Root cause.** `checkSlipFraud` (`lib/chairops/reconcile/slip-ocr.ts:203-259`) sets `requiresReview = true` for a deposit if either (a) `|deposited − collected| >= 500` or (b) the account-number check at lines 246-256 fails. That check strips non-digits via `normalizeAcctNo` (`slip-ocr.ts:190`) from both `configuredAccountNumber` and `ocr.accountNumber`, then required (pre-fix) `a === b || a.endsWith(b) || b.endsWith(a)`. For branch `2aa1207b-...`, the configured account is SCB `813-435083-8` → normalized `8134350838`. The bank's slip masking for this format reveals digits 6–9 of the 10-digit number ("...5083...") — i.e. the *middle*, not the tail (real tail is `...0838`). `"8134350838".endsWith("5083")` is false, so the check falls through to the `!matches` branch and flags every deposit at this branch, every day, regardless of whether the money actually landed in the right account.

Cross-checked against the ฿500-diff rule to rule it out as the trigger: of the 13 rows sampled for the reported branch, 12 had a ฿0 deposited-vs-collected diff and one had -฿72 — nowhere near ฿500 — so the diff rule was not firing; 100% of the flags traced to the account-suffix mismatch.

**Why it produced the symptom.** The account check was added 2026-08-29 (see the adjacent comment in `slip-ocr.ts:242-245`) to replace an earlier account-*name* comparison that had its own false-positive problem (73/73 flagged). That fix correctly moved to comparing digits, but carried forward an unstated assumption — that a masked slip always redacts the front and shows the back — which held for whatever slips were used to validate the 08-29 change, but not for this bank's masking style at these 16 branches. The bug is silent: there is no logging distinguishing "genuinely wrong account" from "masking format not handled," so it read identically to a real fraud flag in the review queue.

**Fix.** Commit `7b56df99` on `claude/chairops-slip-mask-fix-2026-09-20` changes line 249 from `a === b || a.endsWith(b) || b.endsWith(a)` to `a === b || a.includes(b) || b.includes(a)`. `includes()` is a strict superset of `endsWith()`/`startsWith()`-style matching — anything the old check matched, the new one still matches — so it removes the masking-position assumption without narrowing detection. No prior fix attempt exists for this specific bug (the 08-29 change fixed a different, adjacent problem).

**How it was found.** CEO asked why the slip column was red for one branch. Code read of `checkSlipFraud` surfaced two candidate causes: (1) branch bank account not configured (the pattern behind an earlier, superficially similar RentSpace issue, `lib/rentspace/slip-check.ts`'s `evaluatePaymentSlipMatch`, which explicitly treats missing config as "cannot evaluate" → red) or (2) a real recurring discrepancy. A read-only DB query (`weekly_health_check_ro` role) immediately ruled out (1): the branch's `reconcileBankAccountId` was set correctly. Pulling the flagged rows' `ocrFlagReason` text showed the same account-mismatch message on every row, and computing real deposited-vs-collected diffs (mostly ฿0) ruled out the ฿500 rule. Manually diffing the configured account digits against the OCR-read masked digits showed the visible substring sitting in the middle of the real number, not the tail — confirming the `endsWith()` assumption was the mechanism.

**Why it slipped through.** Latent assumption baked into the 2026-08-29 account-number fix: it was validated against whatever slip samples were on hand at the time, all apparently using leading-digit masking, so `endsWith()` looked correct. No test exercises the account-comparison logic against multiple masking positions, and there was no monitoring distinguishing "account check triggered N times" from "genuinely suspicious accounts caught N times," so the false-positive rate climbed silently for three weeks across 16 branches before a CEO screenshot prompted investigation.

**Validation.** `tsc --noEmit`: 0 errors. `eslint lib/chairops/reconcile/slip-ocr.ts`: 0 errors. `next build`: succeeds, all routes collected. Real-data validation via the read-only DB role against 60 days of `ChairopsCashDeposit` rows with `requiresReview = true` and a readable OCR account number (118 rows): replicated both the old (`endsWith`) and new (`includes`) logic in an isolated script. 94/118 rows (80%, across 11 branches) flip from false-positive to correctly-cleared. 0 rows regress (old matched → new no-match), consistent with `includes()` being a strict superset of `endsWith()`. Of the remaining 23 still-flagged rows (6 branches), manual inspection of a sample shows several with account numbers that are genuinely different digit sequences from the configured one (e.g. `594-0-93333-5` vs configured `813-435083-8`, itself a real registered account elsewhere in `ledger_bank_account`) — these still correctly route to human review. A couple of remaining rows look like OCR digit-transposition noise rather than a masking-format gap; the fix fails safe on those (still flagged for a human to check) rather than silently clearing them. Not yet validated in a live deploy — the branch is pushed but not merged to `setup`, pending CEO approval to deploy.
