# Post-mortem: CashHub dashboard stuck on skeleton loaders from an unbounded `branch_health_scores` query

**Summary.** `loadDashboard` in `lib/cashhub/aggregator.ts` fetched the entire history of `branch_health_scores` on every `/cashhub/dashboard` load — no date filter, no `.limit()` — even though only the latest row per branch is used. The table gains one row per active branch every night with no retention cutoff, so the query cost grows without bound as the org ages, and because the dashboard is a single server component with no per-query timeout or Suspense boundary, the whole page hangs behind its skeleton loader indefinitely whenever that one query is slow. Root cause is the same query-shape as the 2026-09-19 whole-ERP Supabase egress-quota lockout (`branch_health_scores` was explicitly flagged there as the pending "Batch 2" item, never fixed at the time). Fixed by adding a 14-day date window plus a `.limit(2000)` safety cap, and separately changed CashHub's root redirect from the broken dashboard to the Data Import Center (`/cashhub/import`) so the page isn't the first thing users hit. Branch `claude/cashhub-dashboard-fix-2026-09-20`, merge commit `dba2af35` on `setup`. **Deployed live 2026-09-21.**

**Symptom.** CEO screenshot of `pooilgroup.com/cashhub/dashboard` showed the "ภาพรวม" (Overview) tab stuck on empty gray skeleton placeholder cards indefinitely — no data, no error, no timeout. CEO independently reported the page "กินข้อมูลตอนเปิดมาเฉยๆ" (consumes data just from being opened).

**Root cause.** `app/(admin)/cashhub/dashboard/page.tsx` is a pure React Server Component (`dynamic = "force-dynamic"`) that awaits `Promise.all([loadDashboard(...), loadExecutiveMatrix(...), loadHotelCardSummary(...).catch(() => null)])` with no per-branch Suspense boundary — `dashboard/loading.tsx`'s skeleton stays mounted until every promise in that `Promise.all` settles, so a single slow/hanging query blocks the entire page with no visible error. Inside `loadDashboard` (`lib/cashhub/aggregator.ts:102-105`, pre-fix):

```ts
safeFrom(admin, "branch_health_scores")
  .select("branch_id, score, grade, computed_for, breakdown")
  .eq("org_id", orgId)
  .order("computed_for", { ascending: false }),   // no .gte()/.lte(), no .limit()
```

`branch_health_scores` is written once per active branch per night by the health-score cron (`app/api/cron/health-score/route.ts:184-190`, upsert on `(branch_id, computed_for)`) with no retention/cleanup job — it is a strictly append-only, ever-growing table. The query above pulls the org's *entire* history of that table on every dashboard load, then dedupes to the first (i.e. latest, since it's ordered desc) row per branch at `aggregator.ts:184-187` — meaning 100% of the rows fetched beyond the most recent one per branch are discarded immediately after fetch. The other queries in the same `Promise.all` (`monthReports`/`prevMonthReports`/`last30Reports` via `loadReports()`, `lib/cashhub/data.ts:160-163`) already carry a `.limit(5000)` safety cap from the 2026-09-19 "Batch 1" fix; this one query was missed.

**Why it produced the symptom.** As the org's history grows (one row per branch per night, indefinitely), this single query's row count and latency grow linearly with calendar time and branch count, with no cap. Once it crosses whatever latency/row-count threshold the RSC request tolerates, the entire `Promise.all` — and therefore the entire page — hangs behind the skeleton, because there is no per-query timeout and no partial-render path (no Suspense boundary isolates this one query from the rest of the page). This is the exact same query-shape flagged as the pending "Batch 2" item in the 2026-09-19 Supabase egress-quota incident post-mortem (that incident's root cause was several unbounded/unfiltered queries hit constantly across the app; `cashhub/aggregator.ts:102` — this exact line — was called out by name in that investigation as "main post-login dashboard query pulls ALL daily branch health-score rows since 2026-05-04... Highest-traffic page in the app," but was never fixed at the time — billing was upgraded and four *other* queries were narrowed instead).

**Fix.** Commit on `claude/cashhub-dashboard-fix-2026-09-20` (merged as `dba2af35`):
1. `lib/cashhub/aggregator.ts` — added `.gte("computed_for", healthWindowStart)` (14 days back) and `.limit(2000)` to the `branch_health_scores` query, matching the existing `.limit(5000)` defensive-cap pattern already used in `loadReports()`. Health scores compute nightly per branch, so 14 days is ample buffer to guarantee at least one row per active branch while making the query's cost bounded and independent of the org's total age. The pre-existing dedup-to-latest logic at `aggregator.ts:184-187` is unchanged — this only bounds what's fetched, not how it's used.
2. `app/(admin)/cashhub/page.tsx` — changed the CashHub root redirect from `/cashhub/dashboard` to `/cashhub/import` (Data Import Center), per explicit CEO request, since the dashboard was unusable as a landing page independent of the query fix. The "ภาพรวม" nav entry was kept (CEO's choice, offered as an explicit either/or before coding) — it is still directly reachable, just no longer the default.

No prior fix attempt exists for this specific query; it was simply missed when the four adjacent queries were narrowed on 2026-09-19.

**How it was found.** CEO reported the symptom via screenshot + description ("dashboard doesn't work, consumes data on open"). A read-only Explore agent was sent to trace the dashboard's data flow end-to-end: confirmed the page is a pure RSC with no client-side fetch (ruling out a hung client request), found the `Promise.all` with no internal timeout/Suspense, and audited every query inside `loadDashboard` for date bounds — `branch_health_scores` was the only one lacking both a filter and a limit. Cross-referenced against the 2026-09-19 egress-incident memory, which had already named this exact file:line as a known-but-unfixed risk, confirming the mechanism rather than treating it as a new hypothesis.

**Why it slipped through.** Incomplete prior fix. The 2026-09-19 investigation explicitly identified this query as the highest-traffic unbounded read in the app and flagged it as "Batch 2" work, but Batch 1 that day only shipped four *other* select-narrowing fixes (chosen because they were zero-behavior-risk column drops); Batch 2 (date-window fixes, which change what data is *shown* and needed a judgment call on safe window length) was explicitly deferred pending further CEO input and was never picked back up until this ticket. There is no test or monitoring on query row-counts/latency for this table, so the degradation was invisible until a user hit a slow-enough case to fully hang the page.

**Validation.** `tsc --noEmit`: 0 errors. `eslint` on both touched files: 0 errors. `next build`: succeeded for all routes, including `/cashhub`, `/cashhub/dashboard`, `/cashhub/import` (verified twice — once pre-merge on the feature branch, once post-merge on the exact commit pushed to `setup`). `git status --porcelain`: clean after commit (only the two intended files changed). Post-deploy live smoke test against `pooilgroup.com`: confirmed a new Vercel deployment picked up the change (response `dpl_` fingerprint changed), then `curl -sI` against `/`, `/login`, `/cashhub`, `/cashhub/dashboard`, `/cashhub/import` all returned expected 200/307 status codes with no 500s. Not validated: the actual authenticated in-browser behavior (does `/cashhub` now land on the import page, does `/cashhub/dashboard` render instead of hang) — unauthenticated `curl` cannot observe post-auth-guard routing, so this needs a real logged-in check, which is pending CEO confirmation. Query latency before/after was not benchmarked numerically (no baseline timing was captured pre-fix); the fix is validated by code inspection (bounded row count, matches an already-proven-safe pattern elsewhere in the same file) rather than a measured before/after number.
