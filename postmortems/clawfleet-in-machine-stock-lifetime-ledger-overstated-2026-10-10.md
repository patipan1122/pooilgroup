# ClawFleet per-SKU in-machine stock overstated ~5.6x org-wide

**Summary.** ClawFleet's stock page showed per-SKU "ในตู้" (in-machine) quantity as the lifetime sum of `LOAD_TO_MACHINE` ledger entries in `cf_stock_movements` — a number that only ever grows, since no movement type exists for a doll being claimed/dispensed by a customer. Org-wide, this inflated reported in-machine stock from a real 3,185 to a ledger-reported 17,898 (5.6x). Fixed by sourcing in-machine quantity from `cf_machines.last_doll_stock` (a trigger-maintained real meter reading) joined through the machine's current active `CfMachineLoadout`. Deployed `origin/setup 3b30d263`, repo `pooilgroup-web`.

**Symptom.** CEO's click-feedback tool flagged that a branch's stated "ตุ๊กตาคงเหลือ" (stock remaining) headline didn't reconcile with the visible per-SKU product list. Investigating that led to the headline number itself being correct, but surfaced a second, separate, more serious problem: the per-SKU "in-machine" breakdown shown in the Overview tab and the main warehouse list was wildly overstated. At branch `2a2fe584-51de-40ff-93e0-b58e51506101`, the UI reported 7,846 dolls "in machines"; the real physical count (sum of each active machine's meter reading) was 853.

**Root cause.** Two independent call sites computed per-SKU in-machine quantity the same wrong way:

- `getCfBranchStockProducts` in `lib/clawfleet/stock-queries.ts`
- `loadWarehouseRows` in `app/(admin)/clawfleet/os/stock/page.tsx` — a duplicate of the same aggregation logic, and the one that actually fed what render on screen (fixing only the first file would not have changed what anyone saw)

Both summed `cf_stock_movements` rows where `machine_id IS NOT NULL`, grouped by `product_id`. The only movement type ever written against a non-null `machine_id` is `LOAD_TO_MACHINE` (written in `lib/clawfleet/actions.ts`, the refill action, lines ~619-634), which records dolls being loaded INTO a machine as a positive quantity moved to that machine. There is no corresponding movement type anywhere in the codebase for a doll leaving a machine via being won/dispensed by a customer. The ledger for `machine_id`-scoped rows is therefore write-only in one direction — it accumulates every refill, forever, and never reflects depletion.

Separately, `cf_machines.last_doll_stock` already exists and is accurate: it's updated by an `AFTER INSERT` trigger on `cf_collection_events` (the real-world event of staff reading a machine's meter during a collection round), and this is the same number the Matrix page and machine-detail views already display and trust.

**Why it produced the symptom.** The ledger-sum and the meter reading measure different things that happened to look like the same concept. `last_doll_stock` is a point-in-time physical count, corrected every time staff actually collect from a machine. The `cf_stock_movements` ledger-sum is a monotonically increasing total of everything ever loaded, with no decrement mechanism. The longer a machine has been in service without this discrepancy being caught, the larger the gap grows — confirmed by the org-wide figure (5.6x) being worse than the single-branch figure originally spotted (3.7x), consistent with different machines having different ages/refill histories.

**Fix.** Rewrote both call sites to compute in-machine quantity as `SUM(cf_machines.last_doll_stock)` for active machines, joined through each machine's current active `CfMachineLoadout` row (`effective_to IS NULL`) to resolve which product that machine currently holds. This is lossless at per-SKU granularity: a direct production query confirmed every machine in the org currently has exactly one active loadout (142 machines with 1, 54 unconfigured test machines with 0, zero with more than 1) — so there is no case today where a machine's stock would need to be split across multiple SKUs with no way to attribute it. `lib/clawfleet/stock-actions.ts` and `app/(admin)/clawfleet/os/stock/stock-client.tsx` were updated to carry the corrected fields through (branch-filter default sync, stock-count detail modal, and a two-equal-groups in-machine/on-shelf display were bundled into the same deploy as separate, unrelated small fixes — see commit `3b30d263` message for full scope). No change was made to how `cf_stock_movements` is written; adding a "dispensed from machine" movement type would be a materially larger feature (it would need to hook into the collection-event path) and was explicitly out of scope for this fix, which is about correcting what gets READ and displayed from data that is already tracked accurately elsewhere.

**How it was found.** Started from a CEO-reported discrepancy between a summary stock figure and a visible product list. Ruled out the headline total as the problem first (it reconciled correctly against shelf-ledger + real machine meters). While checking the per-SKU breakdown underneath it for the same reconciliation, found the "in-machine" figure per product was implausibly large compared to what the Matrix page showed for the same machines. Traced the "in-machine" figure to its source query, found the `cf_stock_movements` aggregation, then grepped for every movement type ever written against a non-null `machine_id` and found only `LOAD_TO_MACHINE` — no corresponding depletion write anywhere. Confirmed the hypothesis with a direct read-only production SQL query comparing the ledger-sum against `cf_machines.last_doll_stock` for the same branch; the gap matched the UI discrepancy. Then found the second call site (`page.tsx`) by grepping for other consumers of the same movement-type aggregation pattern, rather than assuming the one fix location was the only one.

**Why it slipped through.** Latent design gap, not a regression. The ledger-based aggregation was presumably correct in intent at the time it was written — it just was never paired with a corresponding write path for machine depletion, so it was wrong from the day it started being read for display, in a way that wasn't obviously wrong (a plausible-looking number that only becomes implausible once compared against a trusted independent source). No automated check compares the two in-machine data sources against each other, so the drift was invisible until a human looked at both side by side on the same page.

**Validation.** Before/after comparison via direct read-only production SQL (not inference from code review):
- Branch `2a2fe584-51de-40ff-93e0-b58e51506101`: ledger-sum 7,846 → real 853 (matches `cf_machines.last_doll_stock` exactly)
- Branch (second test branch, "เส้นที่ 2"): ledger-sum 5,373 → real 668
- Org-wide: ledger-sum 17,898 → real 3,185

Re-verified AFTER deploy to `origin/setup` (not just pre-deploy in a worktree): queried `cf_machines.last_doll_stock` for the branch directly from production (853), then loaded the live `/clawfleet/os/stock` page as the actual test admin account and summed every "ในตู้" value rendered on the page — 853, exact match. Not retested against every branch in the org individually; validated the org-wide aggregate total and two individual branches directly.

One nuance surfaced during the fix, not a regression: at the individual-product level, a small number of SKUs can show a HIGHER in-machine number under the fix than before, because machines get reassigned to different products over time via `CfMachineLoadout` and the old ledger kept attributing historical load-ins to whichever product was loaded at the time, not what's currently assigned. Branch- and org-level totals are exact either way; only the per-product attribution for machines that have switched products can shift.

**Action items.**
- None filed as follow-up tickets — the fix is sufficient for current use (every machine has exactly one active loadout today). If ClawFleet ever supports mixed-SKU machines, the per-SKU in-machine split would need a design that isn't needed today; worth a note if that feature is ever proposed, not a standing action item now.
- A proper "doll dispensed from machine" movement type (to make `cf_stock_movements` itself a complete source of truth, not just a display-layer workaround) was explicitly scoped out of this fix. Not filed as a ticket — flagging here as the honest reason the underlying ledger still can't answer "how many dolls were dispensed, as opposed to how many were loaded" on its own; only the trigger-maintained meter reading can.
